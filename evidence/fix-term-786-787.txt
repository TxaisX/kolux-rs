fix-term: after.md rows 786 (memory) and 787 (throughput), stress S2 output flood
No app launch. Measured with unit tests and a vitest, debug Rust build (the stress build), one machine, other lanes running,
so the absolute numbers move run to run; the ratios and the bounds are what count.

WHERE THE TIME WENT (row 787), Rust side, 20 MB of 100-byte lines through the per-chunk bookkeeping, per stage (terminal::flood::after787_stage_costs):
  BEFORE (8 KB chunk, original code): base64 215 ms, snap 7, prscan 61, log 1577, history 5286, screen_owner 75   => ~3.3 MB/s in total
  AFTER  (128 KB batch, fixed):       base64 178 ms, snap 2, prscan 33, log 1109 -> 779 (later runs), history 1340 -> 312, screen_owner 67
  - history: the saved-output file was opened for every 8 KB chunk (~1 ms each on Windows) and rewritten (read 256 KB, write 128 KB, rename)
    every 128 KB of output, all under the one registry lock every terminal shares. Now the handle stays open and the rewrite runs once per ~900 KB.
  - log: OutputLog::push copied the whole pending buffer once per line (split_off), and ran strip_ansi char by char on lines with nothing to strip.
  - chunking: the PTY reader read 8 KB and called the handler (two registry lock rounds, a base64 encode, one Tauri event, a file write) per read.
    pty_pump.rs now reads 32 KB on one thread and a second thread hands on everything queued (up to 128 KB) in one call: after787_a_sink_that_costs_per_call_sees_far_fewer_calls
    moved 20 MB in 303-496 calls where 8 KB reads would take 2441.
  Whole bookkeeping, same 30 MB: BEFORE 3.3 MB/s (first run, original code); AFTER 13.3 MB/s (x4, debug). A release build runs this stage roughly ten times faster again.
  (after787_bookkeeping_per_chunk_old_8kb_against_new_batch_128kb now compares 8 KB against 128 KB chunks with the fixed history/log in both; its "old" is no longer the original code.)

WEB VIEW SIDE (src/terminal/outputFlood.test.ts, node, 48 MB): the pane's per-chunk handler (decode, mark scan, gate, address note, ack count) 120-130 MB/s;
  xterm's parser alone (no renderer, scrollback 5000) 19.7 MB/s. Neither explains 0.6 MB/s: the web view is not the bottleneck by itself.

WHAT HELD THE BYTES (row 786):
  The reader's flow control (Flow::sent_within) gave up on a pane that was slow but still answering: one fixed deadline per pause, then the unacknowledged count
  was set to 0 while the pane still had that backlog queued, and a further 512 KB went out on top. Each pause grew the web view's queue (xterm write queue, WebView2 event
  scripts) and the reader's accounting was wrong from then on. terminal::flood::after786_a_slow_pane_that_keeps_answering_never_has_more_than_one_window_queued,
  12 MB to a pane draining ~10 MB/s: peak gap between emitted and drawn BEFORE (old rule kept in the test) 4600-6016 KB, AFTER 504 KB (one window, FLOW_HIGH 512 KB).
  The wait now restarts whenever the pane's acknowledgements make progress and ends only after FLOW_WAIT with none (after786_a_pane_that_answers_nothing_is_still_given_up_on).
  Rust-side retention was already capped and is now pinned by a test (after786_retained_bytes_stay_under_the_caps_and_the_stream_is_whole_and_in_order, 58 MB pushed):
  snapshot tail 131072 B (HISTORY_KEEP), line log 2000 lines, saved history 1031000 B (<= HISTORY_CAP 1 MB, was 256 KB), stream whole and in order (count == bytes, snapshot lines contiguous to the last).
  One uncapped holder was found and capped: OutputLog.pending grew without bound on output with no line break (binary, CR-only progress bars); now cut into lines at 16 KB
  (after786_a_line_that_never_ends_is_cut_at_the_cap).
  Not provable without the app: how much of the 3.4 GB was WebView2/V8 garbage that Chromium keeps in the working set after the queue drains. The backlog bound removes the
  growth that tracked the flood; the stress lane's S2 re-run on main is what closes it.

ORDER AND COMPLETENESS: pty::pump after787_a_numbered_stream_arrives_complete_in_order_in_big_batches (60k numbered lines through reads of 1..30000 bytes and a slow sink: every line present, in order,
  no batch above 128 KB + one read).

LIVE PROOF PENDING (stress lane, S2 on main after the merge): same 8-pane flood; expect all floods done well inside 600 s and peak growth under the 1024 MB bar.
