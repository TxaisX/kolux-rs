3. THE listen() COST (the question asked). Not the registrations and not the webview/IPC being late:
   - first IPC round trip: get_settings 13-20 ms at page boot (m:start -> m:settings); IPC is up at ~900 ms.
   - ~110 invoke() calls leave the page between 1230 and 1370 ms (page clock): ~50 listen() calls from every mounted
     component, plus accounts, usage, agent_list, scm and so on. They all complete in one wave at about 2450 ms.
   - the Rust side of the same run (handler wrapper) shows agent_list, a SYNC #[tauri::command], blocking the UI thread
     for 454 ms (launch 1290-1744), 541 ms (1847-2388) and 481 ms (2877-3358). The page asks for the list three times
     at start (several components call it; App.tsx is one). A sync command runs on the main thread in Tauri 2, and
     every other IPC call, plugin:event|listen included, waits behind it. The first block ends at 1744, the second at 2388,
     which is exactly when p2:listeners fires (2475), so the pane could not begin terminal_spawn before ~2.4 s.
   - same picture in the two other traced runs: agent_list 659 / 559 / 552 ms and 560 / 504 / 502 ms, listeners at +1.17-1.3 s.
   - other handler blocks seen: codex_accounts 109 ms, get_settings 89 ms, shell_list 47-52 ms, guide_mark 28 ms (all below
     300 ms, not touched).
   - the Promise.all of card 6 did nothing because the stall was the UI thread, not the number of round trips.
