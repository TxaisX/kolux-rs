WHAT CHANGED (src-tauri/src/fsops.rs)
- :42-61  identity() on Windows: the entry itself (a link opens as itself: FILE_FLAG_OPEN_REPARSE_POINT; a folder
  needs FILE_FLAG_BACKUP_SEMANTICS; no access asked for): GetFileInformationByHandleEx(FileIdInfo) gives the 64-bit
  volume serial and the 128-bit file id (ReFS, Dev Drives); where a file system has no such id (FAT, exFAT, some
  shares) GetFileInformationByHandle's volume serial plus 64-bit file index. Uses windows-sys, already a dependency
  with Win32_Storage_FileSystem; std's own volume_serial_number/file_index are still unstable.
- :63-67  identity() elsewhere: symlink_metadata's device plus inode (a link counts as itself).
- :69-72  same_entry(a, b): both identities read and equal.
- :86-91  rename(): a name that is taken is refused ("<name> already exists here") when it is spelled exactly as
  given (as before) or when it is not the very entry being renamed. So README.md over readme.md is refused on
  Windows and macOS, and notes.md -> NOTES.md (the same file, new capitals) still goes ahead.

TESTS ADDED (src-tauri/src/fsops.rs tests)
- t616_renaming_onto_another_files_name_in_other_capitals_is_refused: a.txt and b.txt; rename a.txt to "B.txt".
  On a file system that ignores letter case (detected at run time: B.txt "exists") the rename must be refused and
  both files keep their text; on a case-keeping disk (Linux) B.txt is a new name and b.txt is untouched. This is
  the test that fails before the fix on a live Windows run (NTFS) and on macOS: MoveFileExW replaced b.txt.
- t616_a_case_only_rename_of_one_file_or_folder_still_works: notes.md -> NOTES.md and src -> Src; the folder then
  lists exactly "NOTES.md" and "Src", the text intact.
- t616_the_identity_check_tells_one_entry_from_another (the Linux stand-in for a case-insensitive lookup): a hard
  link is the same file under a second name (same_entry true, the rename may go ahead), another file is not, a
  missing name is not, a folder is itself, and a symlink is itself, never its target.
