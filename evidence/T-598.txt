T-598 · Settings never lose what you typed or undo other changes (F02-settings-update.2, .3, .4; SET-036), reliability lane, 2026-10-30

1. F02-settings-update.2: a field reverted to the old text when a save failed.
   Cause: useSettings().save caught every failure and resolved, so useDraft's draft marked the text saved; the page then
   took back the stored (old) value and the not-dirty draft replaced the typed text with it.
   Change:
   - src/settings/useSettings.ts:47-60  save() settles true once stored and false when it failed (after the page shows
     the error and takes back what is stored). It never rejects, so none of its 24 callers outside Settings starts
     leaving unhandled rejections.
   - src/settings/useDraft.ts:10-19     a draft whose save settles false treats it as the failure it is: the typed text
     stays (draft.ts already keeps it on a rejection) and the next pause or blur tries again.
   - src/settings/AgentsPage.tsx:30-31,91  the page's save wrapper passes the flag on; the Draft field hands its save
     straight to useDraft. GitPage needed no change (it passes save()'s promise through already).
2. F02-settings-update.3: the Appearance page wrote back a stale copy of every appearance setting.
   Cause: `look` was read once at mount, and flush wrote writeAppearance(disk, look): all 24 appearance keys, so a
   terminal font size saved on the Terminal card meanwhile was put back.
   Change: src/settings/AppearancePage.tsx:544-580
   - base = the look as stored when the waiting change began; flush writes only
     settingsDiff(writeAppearance({}, base), writeAppearance({}, next)).set; it writes nothing when nothing changed. A
     failed write keeps the base, so the next change tries those fields again; a good one clears the error.
   - The page shows what is stored and follows saves made on any page or window through the useSettings copy it already
     held (Rust broadcasts every settings_patch as settings-saved {set, remove}, lib.rs write_settings), except while
     its own change waits. The page's own get_settings reads are gone; a failed first read still shows at the top.
3. F02-settings-update.4: switching an agent on or off sent the page's whole settings copy as the patch.
   Change: src/settings/AgentsPage.tsx:206-207  the switch sends settingsDiff(settings, switchAgent(...)).set, which is
   only disabledAgents (and defaultAgent "" when the default is switched off).

Tests added: src/settings/settingsSaves.test.ts (the real GitPage, AgentsPage and AppearancePage on the fake DOM
against an in-memory settings store whose settings_patch applies {set, remove} like Rust and can refuse):
  .2  Git page: a commit-instructions text that fails to save stays in the field, the page says why, and the next try saves it
  .2  Agents page: default arguments that fail to save stay in the field for another try
  .3  Appearance page: a change writes only the field it changed, so a terminal size saved elsewhere meanwhile stays
  .3  Appearance page: it follows a save made on another page, so a later change neither shows nor writes the old value
  .4  Agents page: switching an agent off sends only that switch, so a hooks switch turned off elsewhere stays off
Test changed: src/settings/__cards__/SET-001-005.test.ts:152-161 (SET-002 box 2). Its drag goes 100 -> 0 -> 100 inside
  one pause and it waited for a write of themeSaturation 100. That write came only from the bug (every appearance key
  written on any change). Now it asserts nothing is written and the stored saturation reads 100 (the 0 on the way is
  never saved), then that a drag ending elsewhere (0 -> 40) saves exactly {themeSaturation: 40} once.
