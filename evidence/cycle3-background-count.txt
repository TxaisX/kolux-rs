What a user gets:
  - `scm_count` (new command, registered in lib.rs): one `git status --porcelain=v2 --branch
    --untracked-files=all -z`, parsed with the panel's own parser and counted as distinct paths over
    staged, changed, untracked and conflicted files — the same rule the card already used, now in Rust.
    No numstat diff, no untracked line counts, no upstream look.
  - It runs through `spawn_blocking` (off the window thread) and never through `git::foreground`, so
    its short read takes the background turn: a waiting count goes behind the panel on screen and the
    editor's reads on the same worktree (GIT-070's limiter). A source guard in the front-end test and
    the Rust lane test (`proj062_the_card_count_reads_in_the_background_lane`) keep it that way.
  - The window asks `scm_count` and gets a number; it no longer asks for the panel's lists to count them.
  - Slow/blocked read proof: "PROJ-062: a slow or blocked git count never stops the card drawing" holds
    the second read open forever, asserts the card still draws its last count ("2 changed files") and
    the cache does not bump, then releases it and asserts the card shows the new count ("5 changed
    files") with one redraw. The render path (`countFor` + `cardLine`) never awaits the read.
