T-604b (e): the two delete-reading gaps cycle 3 named, closed
=============================================================

Task: cycle 3 assignment 4, "the data-loss gaps: link start points, and -delete after
an escaped group". Files: src-tauri/src/protected.rs only. No dependency, no wire, no UI.

Why these are data loss
-----------------------
A `find ... -delete` that the rule cannot read is a recursive delete that runs without the
protected-action ask. Two shapes were unreadable:

1. An escaped group. The shell reading split the command at every `(` and `)`, including
   `\(` and `\)`, which are find's own group markers. The `-delete` landed in a part whose
   program was not `find`, so no start point was ever judged:
       find .. \( -name x -o -name y \) -delete        ran, though `..` is outside
       find ~  \( -name '*.log' \) -delete             ran, though `~` is outside
2. A link named as a start point. find follows a symbolic link given as a path operand
   (POSIX requires it), while the rule judged only the text. A link inside the workspace
   that points outside passed as "inside":
       find out -delete        with app/out -> /somewhere/else      ran, deleted elsewhere

What changed
------------
* split (protected.rs): an odd run of backslashes before `(`, `)`, `{`, `}` now escapes it,
  so it is not a command separator. `\\(` still splits (even run), real subshells still split.
* find_targets: an escaped group marker (`\(`, `\)`, `\!`, `\,`) ends the start-point list,
  so the words after it are read as find's expression, not as paths.
* start_links_out (new, find -delete only): each start point is canonicalized and compared
  with the canonical workspace; one that resolves outside asks. A path that is not there is
  left to the text check, since it matches nothing. This is find-only on purpose: `rm` and
  `rimraf` remove a link, they do not follow it; find follows a start-point link.
* find -delete with -L (or the older -follow) now asks outright: -L follows links found
  inside the tree too, where no reading can tell where they lead. (-H follows only
  command-line links, which start_links_out resolves.)
* The stale ponytail comment that recorded gap 1 is replaced by the rule it now enforces.

Limits carried forward
----------------------
* The Unix symlink leg did not run on this PC (no symlink privilege, no WSL distro). The
  junction leg proves the same code path on the target platform; the symlink leg is for Linux.
* A start point that does not exist is not canonicalized, so a dangling link inside the
  workspace is judged by its text. find errors on a dangling start point and deletes nothing,
  so this is a false-negative with no loss behind it.
* `-L` now asks for an inside delete too. The rule's user-facing name still reads "Deleting
  folders outside the workspace"; the ask is conservative, the wording is now narrower than
  the rule. Left alone so the rule id and its Settings row do not change.
* No live hook run was needed: the change is in the pure reading that every hook call reaches
  through check(), and the unit tests drive check() with real paths on disk.
