T-033-b evidence (lane/reliability, 2026-10-13). GIT-001: one git status watch per worktree replaces
the Source Control 4 s poll, the diff tab 2 s poll and the All Changes 2 s poll.

How it was measured
- The dev app was launched by `node scripts/evidence/smoke.mjs --only 3 --keep --port 1428 --cdp 9247
  --identifier com.txaisxiong.kolux-rs.reliability.smoke --temp G:\Temp\rel-t033b\live*` (scratch home,
  config, Codex home and KOLUX_APP_DIR under G:\Temp\rel-t033b), so the app has the smoke repo open as a
  project and the Source Control panel showing (flow 3). A harness under G:\Temp\rel-t033b\harness (not in
  the repo) then drove the page over CDP 9247.
- Git processes: GIT_TRACE2 pointed at an empty folder, so every git process the app starts leaves one file
  there (an exact count, other lanes' git never lands in it); plus `Get-Process git` sampled every 500 ms
  for 30 s as the brief asked (that one counts the whole PC, other builders included), plus the git.exe
  processes whose parent is the app, from the same samples.
- Latency: a MutationObserver in the page stamps the time the new row's Discard button appears; the
  harness stamps the time it wrote the file; same clock.

1. Update latency, file write -> Source Control row
   BEFORE (2e6821b, the 4 s poll): 3 writes: min 3194 ms, median 3300 ms, max 3367 ms
   AFTER (watcher):               5 writes: min 870 ms, median 929 ms, max 1570 ms
                                  (first run, while other lanes were building: min 972, median 1128, max 1860)
   Of that, 250 ms is the quiet time the watcher waits for; the rest is the status read itself
   (scm::status runs about 6 git commands, about 70 ms each on this PC).

2. Idle git processes, 30 s, Source Control open, nothing changing
   BEFORE: 114 git processes started by the app (GIT_TRACE2); Get-Process git seen in 27 of 60 samples
           (whole PC, max 14); git.exe children of the app seen in 23 of 60 samples, max 2
   AFTER:  65 and 67 in two runs; Get-Process git seen in 55 and 59 of 60 (whole PC: six lanes were
           building at the time, max 18 / 26); git.exe children of the app seen in 23 and 28 of 60, max 2
   The watcher itself read the status once in those 30 s (its 30 s safety read). The ~65 left are other
   timers of the app, not Source Control: every ~3 s `git --version`, `git worktree list --porcelain`,
   `git symbolic-ref refs/remotes/origin/HEAD`, `git rev-parse main^{commit}`, `git rev-list --count
   main..HEAD` (10 of each in 30 s), and the 30 s scm_summary of VIEW-068 (seen, not changed here).

3. 10k-file checkout with the panel open (branch b holds 10,000 committed files under many/, branch a none;
   notes.txt stays modified across both)
   git checkout a: took 1859 ms; panel right (branch a, 1 change, git status --porcelain says 1) 4873 ms
                   after the checkout began; reads in the next 15 s: 2 (one half-way through at 2473 ms
                   with 7757 changes, one at 4451 ms with the final 1); git.exe children of the app: max 2
                   at a time, 54 git processes in the 16 s window
   git checkout b: took 3367 ms; panel right (branch b, 1 change, git status says 1) 10714 ms after the
                   checkout began; reads: 2 (7791 ms half-way, 10620 ms final); children max 2, 51 git
                   processes in the window
   (An earlier run: right 2496 ms after checkout a began, 17743 ms after checkout b began.) The watcher
   never overflowed on these checkouts (no "source control:" line in the diag log). Each read during the
   checkout takes seconds on 10k files, which is what puts the "right" time past the checkout's end.
   Harness note: the raw event lists below show every event three times because three harness runs had
   each added a listener in the same page; the reads counted above are the distinct ones.

4. Status still right after the watch breaks (KOLUX_DEV_INJECT=watch-error, a debug-only seam: the watch
   breaks on its first change)
   fb-1.txt written: the row showed 622 ms later (the break reads at once)
   the diag log (profile logs/kolux.log) has exactly one line:
     "source control: the watch on G:/Temp/rel-t033b/live2/repo stopped (injected for testing); reading it
      every 4 s instead"
   20 s after the break with nothing changing: 5 status reads (every 4 s)
   fb-2.txt written while polling: the row showed 3313 ms later; panel 3 changes, git status says 3
   Unit tests cover the other break paths: a_reader_whose_folder_is_deleted_reports_the_break (the watched
   folder deleted), a_broken_watch_falls_back_to_reading_every_4_s_and_says_so_once (test seam, two
   breaks, one log line, reads 3.5..6 s apart), a_broken_watch_polls_every_4_s_and_logs_once (the mode).

5. Build churn inside the watched worktree, panel open (churn/ is a crate in the repo; .gitignore has
   target/ and node_modules/)
   60 s, a real `cargo build` of this app into churn/target/ (1237 files written) plus 32,820 files written
   under node_modules/: 2 status reads in the window (2.0 per minute); panel after: 1 change, git status
   says 1
   30 s, back-to-back `cargo clean` + `cargo build` of a tiny crate (25 cycles) plus 500 node_modules files:
   16 reads (32 per minute). Each `cargo clean` first renames target/ to a random name (seen:
   churn/targetO1Jgba) and deletes that, and the skip list matches whole folder names only, so each clean
   costs one read; bounded by the 1 s burst cap (at most 60 a minute). Panel after: right.
