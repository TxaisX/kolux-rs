WHAT WAS BUILT (new shell-owned module src-tauri/src/lifecycle.rs, 12 unit tests; src/shell/closeAsk.ts, 4 vitest)
- APP-001: lifecycle::claim_or_forward runs first in setup, before tools::guarded_setup creates any window.
  The first copy holds a named mutex (windows-sys CreateMutexW, "Local\<identifier>.instance", no new crate)
  for its whole life (managed Instance, closed on drop). A second copy reads the running copy's startup file
  (cli.json: port, token, pid; waits up to ~5.75 s for a copy still starting), grants it foreground rights
  (AllowSetForegroundWindow), asks it over the loopback port with the app.open command (which unminimizes,
  shows and focuses, 5 s answer limit), raises the window itself by pid as a second road (EnumWindows /
  ShowWindow SW_RESTORE / SetForegroundWindow, 5 tries) and exits with code 3, never 0. A mutex that cannot be
  created fails open (the app starts). What the second copy did is written to the diag log.
- APP-002: the terminals run inside this process (no separate terminal service exists in RS), so nothing can
  hold the window back; the page shows the window on its first frames and lib.rs's 5 s fallback (SET-004)
  shows it whatever the page does. Nothing new to build; the wait helper first drafted here was dropped as dead.
- APP-006: the page owns the question. closeAsk.ts: losable(files, agents) is null when nothing would be
  lost (window closes at once); runningAgents counts agent panes still running or starting (running !== false,
  the T-151-c rule), never shell panes, editor/browser tabs or ended agents, and nothing while TERM-045's
  "ask before closing a running terminal" is off; quitQuestion words files first (lost), then agents
  (interrupted). App.tsx (patch): onCloseRequested invokes close_alive at once, then flushes, then asks.
  Rust: on CloseRequested of "main", lifecycle::close_requested starts a 10 s watchdog (ASK_LIMIT): a page
  that never called close_alive for this request is frozen or crashed, and the window is destroyed for it
  (close_verdict: Destroy / Stay / Nothing when already gone). On Destroyed of "main", quit_watchdog gives the
  quit a hard deadline (max(15 s, final-save 5 s + WebView2 wait 3 s + 2 s) = 15 s) and ends the process
  if the final save or the exit wait hangs. Windows menu File > Exit and the tray Quit already route through
  the close request (menu.rs Route::Exit), so they ask the same way.
- APP-011: the Exit handler's final-save steps moved verbatim to lifecycle::quit_steps (activity counts, agent
  status, sign-ins cancelled, Codex and Claude sign-ins sealed). save_point runs them with the same deadline
  and restart_allowed refuses a restart when a step failed or timed out ("The restart was cancelled: the
  save point did not finish (...). Nothing was changed.") or when unsaved drafts would be lost. New command
  app_restart(unsaved) = save point, final_save::begin, kill_all, app.restart. update.rs (patch):
  update_restart takes the save point first and puts the ready update back when it is refused.
- APP-020: lifecycle::fresh_path merges the process PATH with the user and machine Path stored in the
  registry (HKCU Environment, HKLM Session Manager Environment): the process entries first, then stored
  entries not already present (case-insensitive, trailing-slash-blind), nothing dropped or repeated.
  terminal.rs (patch): every pane's PATH goes through it, so a tool installed after the app started is found
  by the next terminal without a restart.
