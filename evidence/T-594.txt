--- review round (PR #5 fresh review, 2026-10-30, integrator)
Finding: KOLUX_PATH_NAME stopped its walk at the first value with an empty name. If HKCU\Environment has its
unnamed default value set, Path was never found and the installer wrote a new Path holding only
$INSTDIR\bin, wiping the user's PATH.
Fix (src-tauri/installer-hooks.nsh, KOLUX_PATH_NAME): the walk ends only on the error flag (set by
EnumRegValue past the last value); an empty name is skipped like any other non-Path value. If the walk finds
no Path, `ReadRegStr HKCU Environment Path` is tried and a value that answers is used, so Path is never
created over an existing one. Only a full walk with no Path and a failed read count as "no PATH".
Header reworded: a PATH stored as REG_SZ is written back as REG_EXPAND_SZ (it does not "stay" REG_SZ).

--- why the app does the uninstall step, not NSIS
NSIS's ReadRegStr/WriteRegExpandStr work on strings of at most 1,024 characters, so NSIS cannot read a
1,815-character PATH at all. Options weighed: (a) System-plugin calls to RegQueryValueExW into a big buffer
plus string surgery in NSIS: possible but every split/compare would be untestable hand-written plugin calls;
(b) PowerShell: .NET's user-environment API expands REG_EXPAND_SZ and can be blocked by policy; (c) the app's
own exe with a flag, running the same Rust code that is unit tested here and that the start-up step uses.
Chose (c). Tauri's template runs NSIS_HOOK_PREUNINSTALL before it deletes the exe, the hook only fires
after the user confirmed, and in update mode the template never runs the uninstaller (PageLeaveReinstall:
"In update mode, always proceeds without uninstalling"; checked in tauri-bundler 2.8.1's installer.nsi).
The exe exits in main() before the window, the single-instance claim or any setup code runs.

--- once per install, and the open question
cli_register itself records nothing on disk: its only record is the PATH value. So the hand-off file IS the
record: the installer writes it, the app consumes it once. If Txais removes the entry (Settings > CLI or
Windows settings), later starts find no file and leave the PATH alone (test below).
An update reruns the installer; if the entry is missing and the PATH is still too long it writes a new
hand-off file and the app adds the entry back. That is the behaviour cli_register/the installer already
have for a short PATH (the cycle-1 note). Open question for Txais, left open: should a removal last across
updates?
