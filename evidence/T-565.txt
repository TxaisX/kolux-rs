T-565 · Escape closes Settings (VIEW-009), reliability lane, 2026-10-30, on lane/reliability (base 025eda2)

Cause (found in the code; the installed build was not run here):
- Settings is drawn over the panes, which stay mounted, and it never took the keyboard when it opened. After
  Ctrl+, the keyboard stayed in the terminal under it. xterm handles a bare Escape itself: it sends ESC to the
  program (an agent reads that as "interrupt") and calls stopPropagation (node_modules/@xterm/xterm/src/browser/
  CoreBrowserTerminal.ts _keyDown -> cancel), so the Settings window listener (bubble phase) never saw it. This
  matches T-544 run 4: "Escape closes Settings: no (opened fresh with Ctrl+, then a CDP rawKeyDown/keyUp Escape)".
- Escape in the xAI key dialog inside Settings (GrokKeyDialog) closed the dialog and then bubbled on to the
  Settings listener, which closed Settings too. The other Escape users inside Settings already stop it (Ask,
  the search box, the font list, the Codex account name field, the chord recorder in the capture phase).

What changed:
- src/settings/SettingsPage.tsx:310-318  Settings focuses its own root when it opens and gives focus back to
  the element that had it when it closes (the terminal it was opened from).
- src/settings/SettingsPage.tsx:329       root gets ref, tabIndex={-1} and outline none (no focus ring around
  the whole page). The Escape listener stays in the bubble phase, so the chord recorder (SET-009, capture
  phase) and every inner dialog keep first claim on Escape.
- src/settings/GrokCard.tsx:149-157       the xAI key dialog stops the Escape it uses.
- src/settings/__cards__/ACCT-008.test.ts:67-72  the shallow test's fake key event gets stopPropagation (every
  real React key event has it) and now also asserts the dialog stops the Escape.
