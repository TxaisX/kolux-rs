T-140-c · council MERGE 50 PRIORITY: a run's usage never bills the user's own session (AUTO-014)
lane/automations from 0819c57 · 2026-10-13

The problem: usage.ts matched a finished run's usage by time window and folder only. An
existing-mode run works in the project's own folder (automations.rs place_and_start, existing
branch: the workspace or project.path), where the user's own all-day Claude session also writes
usage, so that session's tokens were billed to the run.

What is built
- src/automations/model.ts: Run gains an optional sessionId (the agent session the run started).
- src/automations/usage.ts runUsage(run, usage, agentName, mode) and totalUsage(..., mode):
  - with run.sessionId: only that session's rows from the run's start on are matched;
  - without it, a shared folder (mode "existing", or missing as for a deleted automation) reads
    "Unavailable: the run shares its folder with other sessions, and its own session was not
    recorded";
  - a new-per-run worktree is matched by window and folder as before, but more than one session in
    the window reads "Unavailable: more than one session used the run's folder while it ran".
- RunsDashboard.tsx RunPage and AutomationsPage.tsx pass the automation's workspaceMode.
- Nothing records sessionId yet: that needs the hook status reaching automations::on_status to
  carry the session id (hooks lane), filed as open card T-140-e. Until then existing-mode runs
  read unavailable, which is the council's ask.
