What the user can now do: an automation switched to Event > "checks failed" starts a run when the
checks of a pull request open from one of that project's worktrees go from pending (or passing) to
failing. Checks that stay red do not start another run; passing never starts one; an unreadable
reading changes nothing; the first state learned for a pull request is only a starting point.
The five-minute rest after an event and the precheck ahead of the run still apply (on_event).

Blocker in the PLAN line was stale: scm.rs already reports a checks word (GIT-043 checks_word /
checks_of, used by the Tasks search). checks_of is reused as is.

Code, lane side: src-tauri/src/automations.rs
- checks_failed(seen, polled, checks) -> Vec<(path, Pr)>: the pure state machine. seen maps
  "<folder>#<number>" to passing / running / failing. Fires only when the previous known word was not
  failing and the new one is failing. Unresolved or missing word: keep the last state. A closed pull
  request or a different number on the same folder forgets the old entry. Errored rows are skipped.
- checks_round(store, polled, checks): runs one round through the saved state (store key
  automations.checksSeen), so a restart does not refire.
- listens(app, event): is a switched-on automation listening? (the poll looks checks up only then)
- on_checks(app, polled, checks): fires on_event("checks-failed", folder, "Event: checks failed on
  pull request #N from <branch>: <title> <url>"). listens / on_checks carry #[allow(dead_code)] until
  the patch lands.
