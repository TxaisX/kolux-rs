FIX-1 (council fix, not a PLAN card): scm::tests::remote_actions_move_commits_through_a_bare_remote_and_rebased_work_offers_a_lease
Date 2026-10-14, lane/reliability from b33a880 (merge of main d1de182). No app launched.

Problem: the test asserted that three status() reads after "git remote set-url origin <missing>"
finish in under 3 s of wall clock. It failed alone on this PC (3.23 s on the merge tree, 5.8 s
earlier, 10.4 s during this investigation).

Investigation: a test-only hook (git.rs TRACE2 thread-local, cfg(test)) hands GIT_TRACE2_EVENT to
every git the test thread starts, so git logs each process it runs and every child it spawns.
Three status() reads ran 21 processes, all local, the same 7 per read:
  status --porcelain=v2 --branch --untracked-files=all -z
  cherry HEAD @{upstream}
  --version
  symbolic-ref -q --short refs/remotes/origin/HEAD
  rev-parse --git-path rebase-merge ... --git-path REVERT_HEAD
  diff --cached --numstat -M -z
  diff --numstat -z
No child_start events at all: no fetch, ls-remote, remote helper, upload-pack, credential
helper or fsmonitor. Git's own run times (exit t_abs): 75-200 ms each, about 2.3 s summed,
against 10.4 s wall clock for the three reads: the gap is Windows process
start-up on a PC running ~19 other builders. Verdict: purely load; status() never touches the
network. status() itself is unchanged.

Fix: the wall-clock bound is replaced by assertions on the trace2 log: at least three status
processes were logged (the check is not vacuous) and no process or child argv contains fetch,
ls-remote, remote-, upload-pack, credential, fsmonitor or http. A 20 s wall-clock backstop stays:
a hung network call would sit on the OS connect timeout (about 21 s on Windows) and still trip it.
The failure message prints every process and its time.
