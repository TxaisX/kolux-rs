T-552: the relaunch crash in smoke flow 5 (WebView2 0x800700AA, "The requested resource is in use"), lane/launch from 9c09a80 (FIX-3 f741b5a on top of main 243736d)
Lane side done; smoke flow 5 + the stress check run at merge (NO APP LAUNCHES this round).

Where the panic came from (tauri 2.12.1 crate source, read only): the windows in tauri.conf.json are
created inside tauri's own setup step, before the app's setup hook, and any error there ends in
`panic!("Failed to setup app: {e}")` on the main thread. A webview creation error reads
"failed to create webview: WebView2 error: WindowsError(Error { code: HRESULT(0x800700AA), ... })".

WHAT CHANGED
(1) never panic on webview creation or setup: the lib.rs hunk marks the config's windows create=false in the
    generated context and opens them itself in tools::guarded_setup, ahead of the existing setup body (same
    order as before). Any failure there, or in the setup body, or in Builder::build, goes to
    tools::startup_failed: a plain native message box (MessageBoxW, owner-less, warning icon), the APP-003 log
    line "could not start: <reason>", exit code 1. Tauri never sees an Err, so it never panics.
(2) the relaunch retry: tools::open_retrying tries the window, and while the error is ERROR_BUSY
    (0x800700AA, or its signed decimal -2147024726) waits 250, 500, 1000, 2000, 2000, 2000, 2000 ms (9.75 s)
    between tries. Still busy after that: "Kolux is still closing. Try again in a few seconds."
    Any other error is not retried; its message reads "Kolux could not start: <reason>".
(3) quit side (required after smoke-243736d, where 6 msedgewebview2.exe outlived a 3.6 s quit):
    the Exit handler, after every terminal is ended, calls tools::wait_webviews_closed(): up to 3 s, every
    100 ms, it reads the process table and waits until no msedgewebview2.exe child of this app (or anything
    under one) is left. The webviews are already closed by then (the window's removal drops them, which
    closes their controllers, before the event loop ends). A count above 0 after 3 s is logged as
    "app exit: N WebView2 process(es) still running after 3 s (T-552)". WebView2's BrowserProcessExited
    event is not used: reaching it needs the platform webview handle plus the webview2-com crate as a direct
    dependency (a Cargo.toml hunk), so the process table is what is watched.
(4) smoke flow 5: every relaunch waits until the old tree has exited (treeGone after the survivor kill,
    15 s cap), and one stress relaunch now follows the 10-relaunch storm: close over CDP, relaunch the
    moment the pid is gone (no settle, no survivor kill); the page must come up and the app's output after
    that point must not say "failed to create webview", "panicked" or "still closing".
