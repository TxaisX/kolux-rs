T-597 · A slow start never wipes the saved tabs (F05-app-shell-launch.2; VIEW-107, PROJ-067), reliability lane, 2026-10-30

Cause: when main.tsx's settings read lost the 1.5 s race, App started with no tabs and read=false. App's own
settings read then landed and set settingsRead, which opened the layout-save guard (App.tsx:1566
`if (!read && !settingsRead) return;`), but nothing ever put the saved tabs back (restoreLayout ran only in
main.tsx). The first click changed the panes and the empty layout was written over the saved one.

What changed:
- src/main.tsx:37-69  start() keeps the settings read (`reading`) after the race. It draws App through draw(),
  which keys App by `read`. When the race timed out, it waits on: if the settings answer, it applies the
  terminal text (applyText) and runs settle() on them, then draws App again with read=true and the saved tabs.
  A new key means a new App, so its state starts from the saved layout, as on a timely start. If the
  settings never answer, the window stays as drawn (read=false).
- src/main.tsx:71-105 settle(): the steps start() already ran on the settings, moved into one function so the
  late answer gets the same ones: stamp the look on a first start, appearance, language, zoom, restoreLayout +
  stillThere (path_kind) + terminal_prune_history + agent_start_line per agent tab in session order.
  Side effect: after a slow start the saved language, zoom and terminal text now also follow the late answer;
  before, they stayed at the defaults for the whole session.
- src/App.tsx (integrator's file; evidence/reliability-App.patch, NOT committed): the layout-save guard is
  `if (!read) return;`. App's own late settings read no longer opens it; writes start only in the App drawn
  with the saved tabs back.
- Review round 1, also in evidence/reliability-App.patch: src/App.tsx:390-393 `nextKey` starts at 1_000_000 when
  App is drawn with read=false and no layout (before: 2, the same keys the saved tabs use). A tab opened during
  the wait used to take a saved tab's pane key; every pane asks terminal_attach for the terminal of its key
  (TerminalPane.tsx:1023, terminal.rs:1453-1457), and the saved tabs' terminals outlive a quit (APP-052). So the
  wait tab took over that saved tab's running agent or shell, appended its output to history/<key>.log
  (terminal.rs:959), and killed it on unmount when main.tsx drew App again (TerminalPane.tsx:1218-1219); the
  restored tab then found nothing to attach to and started a new process.

Still needs a live Windows run: a start whose settings read takes over 1.5 s (for example a debug delay in
get_settings). Expected: the window shows with no tabs, settings.json's savedLayout is untouched while it shows
(click a workspace meanwhile), and the saved tabs come back with their agents resuming once the settings answer.
Known edge (rewritten in review round 1): a tab opened during the wait gets pane key 1000000 onward, which no
saved tab holds, so it never attaches to a saved tab's still-running terminal or writes into its history. It
closes when the saved tabs come back (it was never saved) and its own terminal ends with it. Its history file
(history/1000000.log) is dropped by terminal_prune_history at the next start that has saved tabs (prune_history
keeps everything when nothing is saved). Cosmetic: such a tab with no folder is titled "Terminal 1000000" for
the few seconds of the wait (TerminalPane.tsx:1469). A live run should confirm: slow start, open a workspace
during the wait, then the saved tabs come back with their agents still running (not restarted).
