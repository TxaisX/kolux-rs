tasks FIX-3 (wave 11, lane/tasks from 322a209 -> main 1c102af4 fast-forward): GitHub host checks refuse when gh's config cannot be read in time
===========================================================================================================================================

WHAT CHANGED (src-tauri/src/github.rs)
- host_allowed no longer fails open. The two config reads (`gh config get -h <host> user`, then
  `gh config get user`) come back as Value / Unset / Failed. Failed = gh could not run or did not
  answer in time. A Failed read on either one refuses the host ("... <host> is not one of them (gh
  did not answer its config read; try again in a moment)"). Before, a failed or timed-out top-level
  read counted as "no top-level user" and the host passed. A refusal is never cached.
- gh_config now runs through crate::scm::gh_config_within, which uses the repo's bounded runner
  (run_within: Windows job object, ends the whole tree at the limit, never only gh). The old
  hand-rolled loop killed only the direct child.
- The equal-to-top-level-user refusal now names the cause ("gh's top-level `user` setting, which
  every host falls back to"), keeping the phrase the scm tests look for (review AFTER 2).

- adds `pub(crate) fn gh_config_within(program, args, limit) -> Result<Option<String>, String>` and
  makes gh_account_within call it. github.rs CALLS IT, so lane/tasks at the FIX-3 commit does not
  compile until this patch is applied: apply it in the same merge. `git apply --check` ok on the
  lane HEAD. Behaviour of gh_account_within is unchanged.
