After-list row 784 (stress S1): a conhost.exe still in the app's process tree 5 s after 40 panes closed, 1 of 5 rounds
Lane fix-other, pass 28, HEAD 79fb8615, read-only diagnosis (no src change). Windows 11 10.0.26300, portable-pty 0.9.0.

1. KILL-PATH SEQUENCE (what happens when a pane closes)
   a. UI -> terminal_kill (terminal.rs:2522; a sync #[tauri::command], so it runs on the main thread)
      -> Terminals::kill (terminal.rs:1254).
   b. terminal.rs:1255 takes the registry mutex (inner) and KEEPS it to the end of the function.
   c. terminal.rs:1256-1266: drops the pane's dirs/marks/keys/hist/owned/snaps and calls flow.release() (1264-1266;
      terminal.rs:292 zeroes the unacked count and notify_all(), so a reader paused for acks goes on).
   d. terminal.rs:1267-1268: sessions.remove(&id) then PtySession::kill() (pty.rs:529), still under the registry lock:
        pty.rs:530  self.writer.take()           drops the input pipe write end (portable-pty dup is the only one)
        pty.rs:531  self.killer.kill()           TerminateProcess on the SHELL only
        pty.rs:532  self.master.take()           last Arc of the master -> ConPtyMasterPty Inner drops -> PsuedoCon::drop
                                                 -> ClosePseudoConsole(hpc) (portable-pty win/psuedocon.rs:73-76), same thread
        pty.rs:533  self.job.take()              closes the pane job (KILL_ON_JOB_CLOSE, procs.rs:109 pane_job) -> every
                                                 other process the shell started is terminated by the kernel
      SizeKeeper holds only a Weak of the master (pty_window_ops.rs:140), so it never keeps the console open; its
      restore thread (pty_window_ops.rs:163-179) briefly upgrades it and ends.
   e. Other threads, none waited on by the closer: pty-reader (pty_pump.rs:25-39) reads its dup of the output pipe and
      sends into a bounded queue of 4; pty-pump (pty_pump.rs:42-60) calls on_output, which takes the registry lock
      (terminal.rs:1092 book_chunk), emits the event, then f.sent() (ACCT-054 flow wait); pty-waiter (pty.rs:459-465)
      blocks in child.wait(), then on_exit takes the registry lock (terminal.rs:1113) and emits the exit event.
   No step waits on a timer. The closer waits on the registry lock (to start) and on ClosePseudoConsole (inside it).

2. WHAT I MEASURED (temporary tests, backed out; logs G:/Temp/fix-other-v3-logs/p28-churn-run*.log, p28-build*.log)
   Counting conhost.exe/OpenConsole.exe whose parent is the test process:
   - Pump stalled on a lock the closer holds (the registry-lock shape) with output queued and the pipe full:
     kill() returned in 0.2-2 ms and the console host was gone in <=1 s (checked at 1, 3, 5, 7 s with the lock still
     held: 0 hosts each time). So on this build ClosePseudoConsole does NOT wait for the pipe to drain, and a
     stalled pump does not hold the host.
   - 40 panes, each cmd /k running a ping child (a two-level tree), killed one after another with PtySession::kill:
     40 kills took 4-12 ms; every host gone after 100-110 ms idle. With 3 `cargo test --lib` loopers plus 16 CPU
     burners (6 runs): kills 11-28 ms, hosts all gone after 358-702 ms.
   Conclusion: the pty.rs/terminal.rs close sequence by itself ends the console host in well under a second, even
   under heavy load, so it cannot explain a host that lives past 5 s.

3. MOST LIKELY CAUSE, AND CONFIDENCE
   A console host lives while ANY client process attached to its console lives. Closing the pane ends the shell at
   once (TerminateProcess) and every other client through the job close, but process teardown is asynchronous in the
   kernel and is slowest exactly in S1 (40 agent/node-sized trees ending together with Defender scanning and a loaded
   PC). A late-reaped client keeps its host for seconds, then both vanish: a gone-by-next-reading 1-3 of 40 matches
   that, and 0 orphans of 424 / 0 survivors at quit says nothing is leaked. Confidence: about 55 % that this is
   slow client reaping (OS side, not our code); about 85 % that the kill sequence above is not the cause on this
   Windows build. Not proven: no reproduction in 8 tree churn runs, the stress run is the only reproducer.
   Second candidate (about 25 %): a pane closed while its spawn is still in flight (the frontend must kill on
   resolve; src/terminal is not in this lane); the host would then live until that late kill.
   Latent hazard that does NOT show on this build (so not the 784 cause here): on Windows builds where
   ClosePseudoConsole waits for the output pipe to drain, terminal.rs:1267-1268 would wait for a drain that needs the
   pump, which needs the registry lock (terminal.rs:1092) that kill holds: a lock cycle, with panes frozen until the
   close times out. Worth removing because it is cheap (section 4).

4. SMALLEST FIX (not drafted: the cause is not clear, per the brief)
   Hardening that is safe regardless: in Terminals::kill take the session out under the lock and kill it after
   dropping the lock:
     let gone = inner.sessions.remove(&id); drop(inner); if let Some(mut s) = gone { s.kill(); }
   (the same in the let_go loop, terminal.rs:1632-1636, which drains under the lock). A 4-line change in
   terminal.rs (fix-term's file), no new test needed beyond the existing kill tests. It does not change the 784
   reading; it only removes the lock-held-during-close shape.
   If the stress proof below shows a client surviving, nothing in Kolux can speed the kernel up; the honest
   change is to relax the harness check (host gone within 15 s, or only count hosts with no live client).
