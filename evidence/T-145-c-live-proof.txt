What was tried (attempt 1, reverted)
- Vendored portable-pty 0.9.0 (crates.io, MIT, LICENSE.md kept) and added one opt-in field,
  ConPtySystem { passthrough: bool }, which ORs PSEUDOCONSOLE_PASSTHROUGH_MODE (0x8) into the
  CreatePseudoConsole flags (the constant already sits in the crate, marked dead_code).
  Two small edits in win/psuedocon.rs and win/conpty.rs; the plumbing in pty.rs was
  open_with_fallback(wanted, open) (flag first, plain console if refused) and
  passthrough_wanted(env, refused). All of it built and its unit tests passed.
- The crate change was small and isolated. The feature did not work.

Measurements (Windows 11 build 26300, inbox kernel32 ConPTY, real PowerShell in a PtySession,
same program run with the flag on and with KOLUX_CONPTY_PASSTHROUGH=0)
- The host ACCEPTS the flag (no error, no fallback taken).
- The pane's received bytes are IDENTICAL with and without the flag. A program writing
  ESC]11;?BEL and ESC]10;?ESC\ never has them reach the pane in either mode (OSC 4 ;?, CSI ?996n,
  CSI ?2031h still do, as TERM-098 measured). The program receives nothing back.
- A sixel DCS (ESC P q ... ESC \) is dropped in both modes, and the screen is repainted
  conhost-style (ESC[K CRLF runs, ESC[?1049h clear) in both: the output is still parsed and
  re-emitted by the console host, which real pass-through would not do.
- Conclusion: on the inbox console host the flag is a no-op. Pass-through is a feature of the
  separately shipped OpenConsole/conpty.dll builds (Windows Terminal), not of kernel32's ConPTY
  on a release Windows. So vendoring the crate and passing the flag cannot deliver the card.

What the card needs instead (judgment call for the coordinator / Txais)
- Bundle a newer ConPTY next to the app: conpty.dll + OpenConsole.exe from Microsoft's public
  Microsoft.Windows.Console.ConPTY package (MIT). portable-pty 0.9 already prefers a conpty.dll
  found beside the executable (win/psuedocon.rs load_conpty), so NO crate fork is needed for that
  part; the flag fork is only needed on top, if that build honours it.
- Open questions that need a real binary and a live run: does that build forward OSC 10/11
  questions (with or without the flag), and does it keep the existing TERM-098 behaviour
  (key-event replies, cursor report)? Cost: two binaries in the installer, a licence line in
  src/assets or NOTICE, a build-time fetch, and a Cargo.toml/tauri.conf.json resource entry
  (shared files).
- Nothing on the webview side is missing: xterm.js 6 already answers OSC 10/11/12 questions from
  the pane theme once they arrive (it does for OSC 4 today), and TerminalPane's write path already
  sends such replies as key events (pty.rs is_reply).
