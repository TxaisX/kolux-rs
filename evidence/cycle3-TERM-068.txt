TERM-068 box 2: switching to another pane while the clipboard is still being read cancels the paste
instead of typing into the new pane. Lane c3-p0-gaps, 2026-10-31.

WHAT WAS WRONG
The chord route hands the clipboard over inside the paste event, in one tick, so it has no window in
which the target can change. The click and menu route (pasteApi in TerminalPane.tsx) calls
navigator.clipboard.readText() itself, and that read is asynchronous. It pasted into the pane it was
started from, never into the newly focused pane, but nothing cancelled it: the text still went into a
pane the user had already left.

WHAT CHANGED
paste.ts gains pasteFromClipboard: after the text read (and again after the image fallback's read) it
asks the pane whether it is still the focused one. Another pane having focus cancels the paste and
nothing is typed anywhere; focus leaving and coming back to the same pane before the text arrives is
not a switch, so the text still goes in. TerminalPane's pasteApi now goes through it, with
focused: () => isFocused.current. Asynchronous pastes also keep the wait-for-the-opening-prompt queue
(pasting.paste), so TERM-068's other rules still hold.
