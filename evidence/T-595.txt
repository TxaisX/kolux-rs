T-595 evidence, 2026-10-30, lane cli (worktree /home/user/kolux-lanes/cli, branch lane/cli)
`kolux open` never pins the caller's folder: Kolux and its background terminal service start in the
program's own folder. Audit R01-cli.4 (cli.rs:1149) and L2-rust-crates.2 (the current-folder leg of the
conpty.dll search). Card CLI-011.

--- what changed
src-tauri/src/pty_service.rs:705-712  new `pub fn start_dir(exe)`: the program's own folder when the program path
    is absolute (always so for current_exe(), which both real spawns use); a relative program path (only a test's
    KOLUX_APP_EXECUTABLE) keeps the caller's folder, because moving would change which file a relative path names
    (Rust's Command docs: a relative program with a new current_dir is ambiguous).
src-tauri/src/pty_service.rs:714-723  `detached()` builds the service's command `exe --terminal-service <id> <data dir>`
    with current_dir(start_dir(exe)); launch_detached (:727) spawns it exactly as before (same flags, same fallback).
src-tauri/src/cli.rs:1135-1151        launch_app picks the app program as before and spawns app_command(&exe).
src-tauri/src/cli.rs:1152-1168        `app_command()` builds that command with current_dir(start_dir(exe)), the same
    null stdio and DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP flags as before.
Arguments: `kolux open` takes no path (OPEN_FLAGS is empty, COMPAT unchanged), so nothing had to be carried over;
the service still gets its data folder (absolute, from app_data_dir) as its last argument, checked by the test.
Before: neither spawn set current_dir, so both processes inherited the folder `kolux open` was run from.
