3. GUARDS
   1. Window/webview/tray/menu: neither touches one. prompt_scan reaches status_inband(AppHandle), which only updates the session map, notes activity and
      emit()s an event; that exact function already runs off the UI thread from the hook server thread (hooks.rs) and the terminal exit thread (terminal.rs).
   2. Order (prompt_scan writes the scan memory and the pane status):
      - the page awaits every call in a pass, in order: prompt_scan_restored, then prompt_scan, per pane, and a `busy` flag skips a pass still running (src/status/promptScan.ts),
        so one pane's restored -> scan order is unchanged;
      - the scan memory (SCANNER) and the session map are each behind their own Mutex, so two overlapping scans cannot corrupt them;
      - the only newly possible interleaving is prompt_scan_pruned (a terminal-exit event, not awaited by the pass) landing while a scan of that same terminal is in flight:
        the scan can then re-create a memo for the ended terminal id. That is a few bytes, overwritten by the next prune/restore, and the same entry the old order produced when a
        scan was issued just after the exit; no status is wrong;
      - the floating panel also calls prompt_scan for the same terminals under other pane keys; two concurrent scans may both see "prompt gone" and both post working, which
        status_inband treats as idempotent (same state, serialised by the session lock). Before, the UI thread serialised them.
      agent_can_install is a read-only PATH probe (like shell_list): no state, no ordering.
   3. Parity tests below.
