What changed (scm_watch.rs)
- Overflow: a change-buffer overflow (ERROR_NOTIFY_ENUM_DIR, or an empty result) is no longer a break. The reader thread issues
  the next read at once and sends Signal::Overflow; the worker treats it as a change (one catch-up read on the usual 250 ms
  quiet / 4 s gap), logs "source control: too many changes at once under <root>; read again, still watching" once, and stays
  Watching. Before: the worktree went to the 4 s poll for the rest of the session.
- Root gone: when a Broken signal arrives, or a read comes due, and the root folder no longer exists, the worker removes its own
  table entry, halts its readers and logs "source control: <root> is gone; its watch stopped" once, then returns. Before: a
  missing folder was read every 4 s forever.
- unwatch_root(path) (new, pub): ends the watch whatever the callers' count, by the path as the project spells it (key() +
  places() fallback, any slashes or case), and JOINS the reader threads so no folder handle of ours is open when git deletes
  the folder. Runs on the caller's thread. A per-watch manual-reset Wake event is part of every reader's wait
  (WaitForMultipleObjects on the read event + the wake event, 500 ms slice), so a stop wakes readers at once.
- unwatch_all() (new, pub): empties the table and halts every watch without waiting (it is called from the window's thread).
- watching flag: Watch.watching is a shared AtomicBool the worker clears on the first break, so a caller joining a watch that
  already fell back is told watching: false.
- packed-refs: Spot::Common = the shared git folder of a linked worktree, non-recursive, only "packed-refs" counts; for a main
  checkout ".git/packed-refs" counts under Spot::Tree. packed-refs.lock, config, FETCH_HEAD, logs/, objects/ still never count.
- Git stays off the typing path: every read still runs on the scm-watch-<id> worker thread; readers are their own threads;
  unwatch/unwatch_all never block; the only joining call (unwatch_root) runs inside the workspace_remove command, which is
  already a background command (it kills processes first).

The 120-a-minute burst in the raw log (T-033-b evidence, line "churn 60 s: ... status refreshes in the window 120 (120.0 per
minute); git processes the app started 404")
  Two numbers, two explanations:
  (1) 120 status reads a minute when the 1 s cap was expected to bound reads at 60: the cap bounds ONE UNBROKEN burst (first
      change + 1 s). The churn loop was 86 `cargo clean` + `cargo build` cycles a minute; at every process start it paused for
      longer than the 250 ms quiet time, and every pause ended the burst and read. So the count was the number of pauses, one
      or two a cycle (86 .. 172; 120 is in that range), and the cap never came into it. T-033-c's 4 s gap between read STARTS
      bounds reads whether the churn pauses or not. Proof: t033e_the_raw_logs_120_reads_a_minute_were_... replays that cycle
      shape (rename, 300 ms pause, 150 ms of writes, 250 ms pause) through Schedule:
      "T-033-e: the T-033-b churn shape: 170 reads a minute without the gap, 14 with it".
  (2) 404 git processes in that minute: one status read is several git processes, not one. Today (trace2 of one scm::status):
      "one status read = 7 git processes: [status --porcelain=v2 --branch --untracked-files=all -z, --version,
      symbolic-ref -q --short refs/remotes/origin/HEAD, rev-parse --verify --quiet main^{commit}, rev-parse --git-path
      rebase-merge ..., diff --cached --numstat -M -z, diff --numstat -z]"; "at most 15 reads a minute = at most 105 git
      processes a minute" from the watcher (the 15 s timer's reads come on top, as in T-033-c's count of 18 vs 15).
      At T-033-b a read was fewer commands (no line counts yet): 404 = 120 reads x about 2.3 + the idle baseline of about
      130 a minute that T-033-b's own "idle 30 s: 65 git processes" line shows.
