# T-223 evidence: TERM-122 keep the computer awake while agents run (also VIEW-097, BROW-053, APP-018)

Lane: launch, from 0819c57. Date: 2026-10-13.

## What was built
- src-tauri/src/awake.rs (new module): the `keepAwake` choice ("off" default, "agent", "on"; an older
  plain true reads as Agent). A watcher thread re-reads the choice and the agent panes' states every
  5 s, so a change, the last agent finishing and a resume from sleep are picked up within a tick.
  Agent holds only while some pane reads working (waiting, blocked, done, permission and
  interrupted do not count); agents are known only from this run, so one marked working before a
  restart but not seen since does not count. Windows: SetThreadExecutionState(ES_CONTINUOUS |
  ES_SYSTEM_REQUIRED) declared through an extern "system" kernel32 block on the watcher's own
  thread (the request belongs to that thread), released with ES_CONTINUOUS; no Cargo.toml change.
  macOS: `caffeinate -i -w <app pid>`; Linux: `systemd-inhibit --what=sleep:handle-lid-switch ...`,
  one at a time, killed on release. A refused call or missing tool does nothing and logs one line.
  Command `keep_awake_state` answers whether the hold is taken now.
- src/launch/KeepAwakeCard.tsx: the Settings > Agents card (On / Agent / Off, Off picked by
  default), help text per choice, and the lid text: "Closing the lid still follows the system: on
  Windows, the lid setting in Power Options decides; a Mac sleeps on lid close unless it is plugged
  in with an outside display; on Linux keep-awake also stops lid-close sleep." Plus useKeepAwake()
  and KeepAwakeItem, the status bar item "Awake" shown only while the hold is taken.
- Not built: the spec's built-in fallback when the macOS/Linux blocker fails (logs once instead);
  a working reading gone quiet past the unverified window still counts (status.rs keeps that flag
  private). TERM-120 (Windows terminals behave natively) is core's: split to T-223-b.
