T-052 · USAGE-001 each agent pane header carries a context ring and a percentage (lane/marks from 243736d, 2026-10-14)

What the user gets: every pane header always carries the context ring and percentage. Until the
first reading comes in it is a greyed 0% whose hover says nothing has been received yet (a shell
pane's hover says agents only); a real 0% reading is shown as a reading, not greyed. The figure
tints yellow from 70% up to 90% and red beyond 90%. Readings are per pane: the newest report takes
the place of the one on screen (even a smaller figure after a compact); a report for a pane that
has closed is dropped; closing a pane or clearing it (a /clear, a resume, a manual compact)
forgets its reading, so the gauge goes back to the greyed 0% until the next report.

"Newest wins": are the reports delivered in order? (the brief asked this before any hooks.rs work)
- Kolux side: the hook server takes one connection at a time on one thread (hooks.rs serve: the
  accept loop handles each stream before the next) and emits the usage event from that thread, so
  the window gets reports in the order Kolux received them.
- Claude Code side (public docs, code.claude.com/docs/en/statusline): "Claude Code debounces
  updates at 300ms ... If a new update triggers while your script is still running, Claude Code
  cancels the in-flight script." So an older report normally never lands after a newer one.
- The remaining late case is across routes: a status report made before a /clear can land after
  the clear's hook event. Arrival order cannot see that, so the window side keeps each reading's
  session and running time when the report carries them and throws away a same-session report
  stamped earlier than the reading on screen, or no later than the reading a clear forgot.
- Today's hook server does not forward those two fields, so the window falls back to arrival
  order (correct for one route). The first hooks.rs hunk (marks-T-052-hooks.patch) is replaced
  by evidence/marks-FIX-1-hooks.patch (see evidence/marks-FIX-1.txt part B): the usage payload
  gains the report's clock, its session id with the terminal that ran it, and
  cost.total_duration_ms, so a resume that keeps the session id while the running time restarts
  is a new clock; compiled and tested on a scratch worktree, with a hooks.rs test.
