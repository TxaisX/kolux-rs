ITEM 4 - hard links and per-file-symlinked dotfile setups (review AFTER 1 and 2), stated plainly
  Hard link: containment goes by path. An NTFS (or Unix) hard link inside the folder to a file elsewhere on the same volume has no other path, so it is READ like any file in the folder. No privilege is needed to make one. Pinned by a characterization test, not a wish:
    term_099_fix3_a_hard_link_inside_the_folder_is_read_because_containment_goes_by_path (passes before and after; it documents the limit)
  Per-file symlinks (GNU stow, home-manager into /nix/store, a dotfiles repo linked file by file): the first config file may be a link, but an include or theme or Warp file that is itself a link to a place outside the folder is refused and listed by bare name as "is outside the configuration folder" / "is outside the theme folder". That is deliberate (the same rule that stops a link to a private file). A whole folder that is a link is fine. A user with a per-file setup sees the warning line and can put the files in the folder.
  The PLAN T-307 wording was re-read: it says containment is "after symlinks and junctions are resolved" and, with this round, names the exceptions.
