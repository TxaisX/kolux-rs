What a user gets:
  - A recursive delete whose start point is a folder link asks. Once normalized, `rm link` and `rm link/`
    (which follows it) cannot be told apart, and `find link/` follows; a junction on Windows counts as a
    link. A link on the way is resolved: one that stays inside the workspace (and out of .git) runs, one
    that leads out, into .git, or nowhere asks. Paths with no link on the way are judged as before.
  - `find ... -delete` is now found even when the reading splits at `(`/`)`: the expression parts after an
    escaped group are put back before find is judged (a command never starts with `-`, `!` or `,`, nor with
    the lone `\` the split leaves). So `find .. \( -name x -delete \)` asks, while `find . \( ... -delete \)`
    still runs.

The test is platform-honest: the link is `std::os::unix::fs::symlink` on Unix and `cmd /C mklink /J` on
Windows (no admin), and every path in the command is joined with MAIN_SEPARATOR so the Windows two-way
reading sees one spelling. protected_custom.rs's tests were read (they cover masking and the attempts
list) and stay green in the 88.
