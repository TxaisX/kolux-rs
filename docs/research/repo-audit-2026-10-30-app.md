# Kolux RS audit, 2026-10-30: every finding in the front end, security, process, tests and libraries

This is part of the detail behind [the audit report](repo-audit-2026-10-30.md). The rest is in [every finding in the Rust back end (R01 to R10)](repo-audit-2026-10-30-rust.md) and [every ponytail note](repo-audit-2026-10-30-ponytail.md). Each entry carries enough detail for whoever fixes it; the report is the place to start.

**How each finding was checked.** One auditor read each area and wrote findings. Every finding the auditor rated critical or high then went to two separate reviewers told to refute it: one traced the actual code path, the other asked whether it can really happen in the shipped Windows app and whether the spec meant it. Findings rated medium went to one reviewer, in batches of up to six. Findings rated low were not double-checked. When reviewers disagreed on how serious a finding is, "Severity after checks" is the lowest rating from any reviewer who agreed it was real. Refuted findings are listed at the end of the front-end file so nobody reports them again. IDs such as `R01-cli.2` follow each auditor's own numbering, so the list below is sorted by severity but the numbers are not always in order.

**Totals for the whole audit.** 194 findings from 25 code, security, process, test and library auditors. By check: 104 confirmed, 85 unverified, 1 uncertain, 4 refuted. Severity after checks, refuted ones left out: 12 high, 73 medium, 105 low.

Probe scripts and logs the auditors used existed only during the audit; they appear as "an audit test file" or "the audit's own check log".

**Words used here.** Worktree: the separate folder git makes for each Kolux workspace. CI: GitHub's automatic build-and-test run. Hook: the small script an agent runs to tell Kolux its status and to ask before a risky command. npm: the Node.js package installer. cmd.exe: the old Windows command prompt. Lock: while one part of Kolux holds it, every other part that needs the same data waits.

## F01-editor: Editor, previews and document views

The editor area is built hard around not losing work. Saves are checked against the disk copy, drafts survive crashes, closing tabs asks first, and the rich Markdown view refuses edits it cannot place. The PDF viewer, diagram and maths rendering, and the file fence are well locked down. The most serious problem is that the Markdown preview puts a repository's HTML straight into the app's own page. A README with a &lt;style&gt; block can blank out or restyle the whole window, and the effect returns after every restart because preview tabs are restored. The same renderer is used for agent plans and chat (PlanSheet.tsx, StepRows.tsx, other slices). On Windows, where Git normally checks files out with CRLF line endings, typing new lines in the rich view saves them with bare LF endings and makes the source view show merged lines. The same root cause means a file whose line endings an agent or formatter changes can collapse into one line in an open tab. The rich view's table support can silently delete cell text after a user types a | into a cell, or when a row has more cells than its header. I reproduced this and the line-ending bug with the real code in a scratch harness: an audit test file and run5.mjs in an audit test. The tests are extensive, but the line-ending test feeds the rich-view code a CRLF buffer the app never actually has, which is how this slipped through. Cross-slice notes: git.rs diff\_bytes reads the working file with no size cap. Pasting LF text into a CRLF file probably hits the same separator problem, depending on the clipboard's line endings on Windows (not verified).

**What is done well:**

- The save path refuses to overwrite a file that changed on disk: a loaded-hash check under one Rust write lock, a disk-change banner, an undoable Reload and an explicit Keep mine choice. Autosave stands down while the banner is up or a move is in progress.
- Unsaved text is kept as a draft 600 ms after typing stops and flushed on blur, hide and reload. The close guard covers every close path, including the floating panel, and saves only the tabs it can.
- The rich Markdown view refuses edits it cannot place. In my headless runs, word-mapped placement plus byte-window and list-shape invariants kept hard breaks, link titles, ordered-list starts, &lt;br&gt; in cells, \_emphasis\_ and entities byte for byte. Content it cannot show opens in source view with a reason.
- The PDF viewer is locked down: no eval, scripting, XFA, fetch or downloads; link clicks go through a filter that opens only web links; middle-click is blocked. pdf.js is current (5.4.624).
- Mermaid diagrams render in an empty-sandbox iframe with its own CSP, KaTeX runs with trust off and its output is sanitized, and SVG files are drawn through &lt;img src=blob:&gt; so their scripts never run.
- The main window's navigation guard sends web addresses to the system browser and drops file: and other schemes. The Rust fence refuses UNC, WSL and device paths by spelling before touching them, so file://server links in notes cannot reach a network share.
- Effects clean up their listeners, observers and timers consistently, and stored per-viewer data (localStorage) is parsed inside try/catch.

**Not reviewed in this area:** src/editor/richDetails.ts; src/editor/richFormat.ts; src/editor/richKeys.ts; src/editor/richCode.ts; src/editor/richCodeColour.ts; src/editor/richDraw.ts and DrawPanel.tsx (grep only); src/editor/slashMenu.ts, SlashPanel.tsx, wikiPopup.ts; src/editor/TableControls.tsx, tableHover.ts, RichToolbar.tsx; src/editor/NoteTools.tsx, NoteRail.tsx, ReviewNotes.tsx, notes.ts, notefind.ts, rail.ts; src/editor/diffNotes.ts, oldSide.ts, copyContext.ts, allChangesCopy.ts, changeConflicts.ts, conflicts.ts; src/editor/ChangeTree.tsx, ContentSearch.tsx, search.ts, searchSeed.ts, FilePicker.tsx, pickerSearch.ts, SearchPick.tsx, settledQuery.ts; src/editor/CsvTable.tsx, csv.ts, ImageCanvas.tsx, LinkHover.tsx, linkBubble.ts; src/editor/templates.ts, TemplatePicker.tsx, NamePrompt.tsx, firstSave.ts, desktopDrops.ts; src/editor/explorerBar.ts, FileIcon.tsx, fileIcons.ts, languages.ts, openIn.ts, openInEdit.ts, logFollow.ts; src/editor/sectionWindow.ts, useSectionWindow.ts, viewSwitch.ts, AddProjectRow.tsx, fileLineKeeping.ts, richSaveSeedCases.ts; CSS files and the remaining test files.

### F01-editor.1 Markdown preview puts a repository's HTML into the app's own page: &lt;style&gt; rules, full-window overlays, image-map links and forms get through

- **Severity after checks:** medium (the auditor said high) · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** security
- **Where:** `src/editor/PreviewPane.tsx:32`
- **What you would notice:** Previewing a README from a downloaded repository can blank out the whole Kolux window or show fake messages, and the problem comes back every time the app restarts.
- **How it happens:** A cloned repo's README.md contains `<style>body *{visibility:hidden!important} body::after{content:"Session expired - run setup.ps1 in a terminal";visibility:visible;position:fixed;inset:40%}</style>`. marked 18.1.0 passes it through unchanged (verified by running it). DOMPurify 3.4.16's default profile keeps &lt;style&gt;: it is on the allow list at purify.es.mjs:280, and \_isUnsafeNode only removes a style whose text holds markup. The CSP allows inline styles (tauri.conf.json:28, style-src 'unsafe-inline'). The preview is injected into the main document (line 211), not an iframe or shadow root, so the rule applies to the whole app. It applies even while the preview tab sits in the background, since `hidden` only hides the section. Preview tabs are saved and restored at startup (src/terminal/layout.ts:16, 113-116), so a restart brings the blank window back. The same default profile also lets through: inline `style="position:fixed;inset:0;z-index:..."` overlays covering the window (fake prompts); `<map><area href>`, where a plain click navigates because the guard at line 209 only checks closest("a") (https goes to the system browser via menu.rs:303; a relative href reloads the app, since Tauri serves index.html for unknown paths); and `<form><button>`, where the CSP has no form-action and a submit GETs the app's own origin, which the navigation guard allows, so the app reloads. DECISIONS.md DT-R14 says "the preview is marked plus DOMPurify and its links are inert". No test feeds hostile HTML to renderMarkdown. The same function renders agent plans (src/terminal/PlanSheet.tsx) and chat steps (src/chat/StepRows.tsx), so agent output can do the same.
- **Code:** `export const renderMarkdown = (md: string) => filterDataPictures(DOMPurify.sanitize(marked.parse(md, { async: false }))); ... if ((e.target as HTMLElement).closest("a")) e.preventDefault(); // line 209 ... dangerouslySetInnerHTML={{ __html: html }} // line 211`
- **Suggested fix:** Best fix: render the preview in a sandboxed iframe (srcdoc, no allow-scripts and no allow-same-origin, with its own CSP) and pass link clicks out with postMessage. Minimum fix: call DOMPurify with FORBID\_TAGS \["style","form","input","button","select","textarea","map","area","dialog"\] and FORBID\_ATTR \["style","popover","popovertarget","command","commandfor"\], cancel the default action of every click inside the page (not only &lt;a&gt;), and add `form-action 'none'` to the CSP. Add a test that renders a hostile note.
- **Reviewer (confirmed, high):** I read the whole path and then ran it, and every claim in the finding holds. \*\*How the code gets there\*\* - The preview is built at PreviewPane.tsx:64 as `renderNote(body, renderMarkdown)`. - `renderNote` (diagrams.ts:169-172) only swaps maths spans out and back. - `renderMarkdown` (line 32) runs `DOMPurify.sanitize` with no config. - The result goes into the main document through `dangerouslySetInnerHTML` (line 211). There is no iframe and no shadow root. - Nothing narrows DOMPurify's defaults. (shortened)
- **Reviewer (confirmed, medium):** What I checked: (1) The sanitiser. renderMarkdown calls DOMPurify 3.4.16 with no options. Nothing in src/ calls marked.use, setConfig or addHook, so the default profile is what runs. That profile allows style, form, input, button, map, area and dialog, and the attributes style, action, href and usemap. \_isUnsafeNode only removes a &lt;style&gt; whose text contains markup or "&lt;/style". (shortened)

### F01-editor.2 Rich-view edits write bare LF line endings into CRLF notes and garble the source view

- **Severity after checks:** medium (the auditor said high) · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** bug
- **Where:** `src/editor/EditorPane.tsx:531`
- **What you would notice:** On Windows, adding lines to a README in the normal rich view saves them with different line endings from the rest of the file, and the Source view then shows those lines jammed together with red dots.
- **How it happens:** Git for Windows checks Markdown out with CRLF by default (core.autocrlf=true). Line 345 builds the CodeMirror view with lineSeparator "\r\n", but the rich view reads cm.state.doc.toString(), which always joins with "\n". So inFileEnds (frontMatter.ts:71-74) never sees "\r\n" and keeps the "\n" from the rich view's output. CodeMirror then splits the insert only on the configured "\r\n" (@codemirror/state 6.7.6 dist/index.js:972), so the new lines become characters inside one line. I ran the real richChange against a CodeMirror state built exactly as at line 345 (scratch an audit test file). Typing a new paragraph into "# Title\r\n\r\nFirst paragraph.\r\n\r\nSecond paragraph.\r\n" saves "...First paragraph.\r\n\r\nA new paragraph typed in the rich view.\n\nSecond paragraph.\r\n", and CodeMirror holds 6 lines for an 8-line file. The source view then shows the new paragraph glued to the next line with red special-character dots (basicSetup highlightSpecialChars). Path:line jumps, search hits, review notes and Copy Context line ranges are off by the merged lines. The LOW-3 test (richSaveGuards.test.ts:485-498) passes real CRLF text as `now`, a buffer the app never produces, so it passes while the app misbehaves. NotebookView's onText (line 894) has the same mismatch: a cell edit in a CRLF .ipynb turns the whole notebook into one source line.
- **Code:** `const now = cm.state.doc.toString(); // always joins lines with \n ... cm.dispatch({ changes: change, userEvent: "input" }); // line 536 // frontMatter.ts:73 if (!bare(before === "\r" ? "\r" + insert : insert) || bare(now) || !now.includes("\r\n")) return insert;`
- **Suggested fix:** Feed the rich view and richChange the file's own spelling (cm.state.sliceDoc()), or convert each insert to cm.state.lineBreak before dispatching (insert.replace(/\r?\n/g, cm.state.lineBreak)). Do the same for NotebookView.onText. Add a test that goes through a real EditorState configured with lineSeparator "\r\n".
- **Reviewer (confirmed, high):** I followed the code path from start to end and ran it against the real libraries. The claim holds. The path: 1. EditorPane.tsx:345 builds the view with lineSeparator "\r\n" whenever the file text read from disk contains CRLF. file\_read hands back the bytes unchanged (files.rs:38-52), so a CRLF note does reach the editor as CRLF. 2. The rich view is fed `cm.state.doc.toString()` (line 520), and its edit callback also reads `doc.toString()` as `now` (line 531). (shortened)
- **Reviewer (confirmed, medium):** The bug is real, and an ordinary user hits it in the shipped Windows app. I lowered the severity from high to medium because no content is lost. How it happens. A CRLF file gets a CodeMirror state whose line separator is "\r\n". The rich view and richChange are both given cm.state.doc.toString(), which always joins lines with "\n". The Lexical export (`out`/`prev`) also uses "\n". So `now` never contains "\r\n", and inFileEnds returns the insert unchanged. The guard is dead code in the app. The insert is then dispatched with "\n" in it. (shortened)

### F01-editor.3 Rich view silently deletes table cell text: a typed | is saved unescaped, extra cells are hidden, and the next edit of the row drops them

- **Severity after checks:** medium (the auditor said high) · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** data-loss
- **Where:** `src/editor/richTable.ts:269`
- **What you would notice:** Typing a | character into a table in a note, or editing a table row that has an extra column, can silently delete text from the file the next time that row is edited.
- **How it happens:** Cell text is written back exactly as typed: neither rowLine nor respellRow escapes "|". On import, a row keeps only as many cells as the header (line 255). When a row holds more cells, respellRow returns null because the count differs, and the export falls back to the canonical line built from the visible cells only (line 269). The save guards treat the missing text as part of the user's edit. I ran the real TABLE transformer and richChange headlessly (scratch an audit test file): (1) In the row "| du | disk use |", typing "lists files | sort" into the second cell saves "| du | lists files | sort |"; GitHub already drops "sort" when rendering. (2) After reopening, the rich view shows only \["du","lists files"\]. (3) Editing the first cell saves "| ls -la | lists files |", and "sort" is gone from disk. A hand-written row "| 1 | 2 | note: keep me |" loses "note: keep me" the first time cell A is edited. unsupported() and richBlocker() return null for these notes, so they open in the default rich view, and placeStats shows no refusal.
- **Code:** `export const rowLine = (cells: string[]): string => '| ${cells.join(" | ")} |'; // line 63, no escaping const cells = splitRow(lines[i]).slice(0, heads.length); // line 255 lines.push(r.__raw ? (r.__canon === canon ? r.__raw : (respellRow(r.__raw, splitRow(r.__canon), cellTexts(r)) ?? canon)) : canon); // line 269`
- **Suggested fix:** Escape | (as \\|) in cell text on export. On import, either keep cells past the header count or open such tables in source view with a banner. In the export, when respellRow cannot match the cell count, keep the raw row (refuse the edit) instead of writing the canonical line. Add the three cases above as tests.
- **Reviewer (confirmed, high):** I traced the whole path: import, show, edit, export, placement, the invariant and the save. Then I reproduced it with the real sources, transpiled into a new scratch folder (my own copy, not the earlier agent's). How the code behaves: 1. Import keeps only the header's number of cells (richTable.ts:255). It stores the full line as `__raw` and a canonical line built from the shortened cells as `__canon` (richTable.ts:224, 257). 2. If the row is not edited, export writes `__raw` back (line 269), so the round trip is faithful. (shortened)
- **Reviewer (confirmed, medium):** The finding stands. The user can trigger it in the shipped app, nothing stops it, and it is not intended. The severity is overstated, though: medium fits better than high. \*\*Reachable.\*\* Markdown files open in the rich view by default. A typed `|` goes into the cell's text unchanged. registerTable handles only Tab, Enter, Backspace, Delete, Arrow Down and Paste. The markdown shortcuts run without the TABLE transformer, and TABLE.replace returns false. Nothing else in src touches cell text. (shortened)

### F01-editor.4 Line ending is fixed when a tab opens: mixed files merge lines, and a file rewritten with other line endings collapses into one line

- **Severity after checks:** medium · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** bug
- **Where:** `src/editor/EditorPane.tsx:345`
- **What you would notice:** When an agent or formatter changes the line endings of a file you have open, the whole file can suddenly show as one huge line, and clicking a file:line link can land on the wrong line.
- **How it happens:** With a configured separator, CodeMirror splits text only on that separator (@codemirror/state dist/index.js:2761) and draws a lone \n as a special-character dot (@codemirror/view Specials, dist/index.js:9900). I measured both cases with a real EditorState (scratch an audit test file): (a) A 300-line CRLF file is open in front. An agent or formatter rewrites it with LF (Prettier's default is LF). The clean tab reloads quietly (diskChange.checkOnce -&gt; replaceAll), and CodeMirror now holds ONE line of 2,605 characters. With word wrap on, a big file becomes very slow. (b) A CRLF file where an agent inserted three LF-only lines opens with them merged into one line ("new a\nnew b\nnew c\nline 11"). Every later line number is off by 3, so path:line links and search hits land on the wrong line. The reverse (an LF tab receiving a CRLF rewrite) shows a dot at the end of every line. The bytes are preserved, and reopening the tab fixes the view. DiffPane.tsx:310/389 and the followed-log tab (line 691) use the same rule.
- **Code:** `extensions: [EditorState.lineSeparator.of(text.includes("\r\n") ? "\r\n" : "\n"), ... // buffers.ts:119 (quiet reload, Reload button, followed logs) for (const v of b.views) if (v.state.sliceDoc() !== text) v.dispatch({ changes: { from: 0, to: v.state.doc.length, insert: text }, annotations });`
- **Suggested fix:** Re-detect the line ending on every load and replaceAll, and reconfigure the separator through a Compartment. For mixed files, use the default splitter and remember the dominant ending for writes. Add a transactionFilter (and a clipboardInputFilter for pastes) that rewrites inserted line breaks to state.lineBreak.
- **Reviewer (confirmed, medium):** EditorPane.tsx:345 picks the separator once from the first read. lineSeparator is a static facet (@codemirror/state dist/index.js:2045), the editor effect only re-runs on \[id, path, tries\] (EditorPane.tsx:406) and the tab key is stable (App.tsx:2984). (shortened)

### F01-editor.5 Sanitized preview HTML is rewritten afterwards by regex (maths placeholders, data pictures), which can break out of attributes

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** security
- **Where:** `src/editor/diagrams.ts:165`
- **What you would notice:** On current Windows this only garbles how a note looks when it has maths inside HTML. On older Mac or Linux systems, a crafted note could bring back page elements the cleaner had removed, though it still cannot run code.
- **How it happens:** renderNote (PreviewPane.tsx:64) runs restoreMath on DOMPurify's output. A `$x$` inside an HTML attribute (e.g. `<img alt="$a$ <img src=x onerror=...>">`) becomes a placeholder that DOMPurify keeps. restoreMath then inserts `<code class="md-math-src">...` into the attribute, and its first quote ends the attribute and the tag. Chromium 138+ (current WebView2), Firefox 140 and Safari 26 escape &lt; and &gt; inside attributes when serializing, so the rest becomes junk text, and the CSP's script-src 'self' blocks inline handlers anyway. On older WebKit (pre-Safari-26 macOS, older Linux WebKitGTK), the remainder is parsed as markup, re-creating elements DOMPurify had removed (iframes, meta refresh, etc.). On those engines, filterDataPictures' `[^>]*>` can also end inside an attribute value.
- **Code:** `return html .replace(/<p>KXMATH(\d+)X<\/p>/g, ...) .replace(/KXMATH(\d+)X/g, (m, n: string) => (items[+n] ? one(items[+n]) : m)); // notePictures.ts:47 html.replace(/<img\b[^>]*?\bsrc\s*=\s*(["'])(\s*data:[\s\S]*?)\1[^>]*>/gi, ...)`
- **Suggested fix:** Do the maths substitution and the data-picture check on DOM nodes or in a DOMPurify hook or marked extension, then sanitize once as the last step. Never string-edit HTML after sanitizing.

### F01-editor.6 Every keystroke compares the whole file twice with regexes, so typing in a multi-megabyte file lags

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** performance
- **Where:** `src/editor/buffers.ts:84`
- **What you would notice:** Editing a large file, such as a big JSON or log of several megabytes, makes every key press visibly slow.
- **How it happens:** Each transaction calls tell(), and EditorPane's subscriber then calls isDirty(path). That builds the whole text with sliceDoc() and, once the text differs from disk, runs two regex passes over both copies. I measured sameText alone at about 145 ms per keystroke on a 10.2 MB file (scratch an audit test file), and text files up to 32 MB open (files.rs TEXT\_MAX). 600 ms after each pause in typing, the draft flush adds another full sliceDoc, a SHA-256 of the disk copy and a 10 MB IPC message (drafts.ts:53-68).
- **Code:** `const norm = (s: string) => s.replace(/[ \t]+(?=\r?\n|$)/g, "").replace(/\s+$/, ""); // line 16 ... return !!v && !sameText(v.state.sliceDoc(), b.disk); // line 84`
- **Suggested fix:** Track dirtiness cheaply: compare against the saved document only when it matters (on save or reload), or keep a changed-since-save flag plus a length check. Skip or debounce draft writes above a size limit.

### F01-editor.7 PDF tab recomputes every page position in quadratic time and re-renders every page on each scroll event

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** performance
- **Where:** `src/editor/PdfView.tsx:146`
- **What you would notice:** Scrolling through a very long PDF, thousands of pages, stutters.
- **How it happens:** onScroll (lines 163-172) always calls setPos with a new object. So every scroll event re-renders PdfView, recomputes `tops` in O(n^2) and reconciles all page components (PageCanvas is not memoized). I measured the position math alone at 14 ms per scroll event for 2,000 pages and 66 ms for 5,000 pages (scratch an audit test file). A text-heavy manual of a few thousand pages fits under the 32 MB read limit (files.rs BYTES\_MAX).
- **Code:** `const heights = Array.from({ length: pages }, (_, i) => sizeOf(i + 1).h * scale); const tops = heights.map((_, i) => heights.slice(0, i).reduce((a, h) => a + h + GAP, GAP));`
- **Suggested fix:** Compute tops with a running sum inside useMemo keyed on sizes and scale. Skip setPos when the page and offset did not change. Wrap PageCanvas in React.memo.

### F01-editor.8 Closing one of two tabs showing the same file deletes the crash-recovery draft the other tab still needs

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** data-loss
- **Where:** `src/editor/useFileMoves.ts:25`
- **What you would notice:** If you close a duplicate tab of a file with unsaved changes and the app then crashes, the changes in the tab you kept are not recovered.

Choosing Don't save leaves the text in the other pane, but App.dropPanes calls discardDraftsOf. - **Suggested fix:** In discardDraftsOf, skip paths that a staying tab still shows, as closeGuard.unusedNotes already does. Or re-flush the draft for any buffer that is still dirty after a discard.

### F01-editor.10 Local pictures in a Markdown preview never load on macOS or Linux

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** cross-platform
- **Where:** `src/editor/imageFiles.ts:127`

## F02-settings-update: Settings, update, feedback, i18n and setup screens

The settings, update, feedback and setup code is careful at its core. The backend merges partial saves under one lock and writes atomically, secrets never reach the window, the trust prompt fails safe, and the feedback scrubber is fast and broad. The most serious problem is in the update card. After you collapse it, or after one failed background download, every half-hourly background check reopens it and takes the keyboard. In the "ready" state, an Enter meant for an agent then restarts Kolux to install, ending all running agents. The settings saves have three ways to lose your input: a text field quietly reverts to its old value when a save fails, because the shared save never reports failure; the Appearance page writes back a stale copy of the terminal font settings when the Settings search shows it next to the Terminal page; and switching an agent on or off re-saves the page's whole settings copy, which can undo changes made by backend commands that never announce their saves. Problems outside this slice that feed into these: agent\_creds.rs, projects.rs set\_place, claude\_key.rs and the `kolux agent hooks` CLI write settings without emitting settings-saved, and launch/agents.ts switchAgent returns the whole settings object. Smaller items are a number field that cannot be typed into normally, emails and xAI/Groq keys slipping through the feedback scrubber, and translated text that stays English until something else redraws the screen. Hardening note only: the trust prompt shows kolux.yaml scripts raw, with no warning for invisible or right-to-left control characters.

**What is done well:**

- scrub.ts runs in linear time even on 40 000-character pathological lines (timed on a scratch copy). It is idempotent, masks many Windows path forms (UNC, \\\\?\\, WSL, Git Bash, quoted user folders with spaces) and common token shapes. The crash bundle is scrubbed again on top of the backend's own masking.
- Settings saves are deltas against a fresh disk read, queued one at a time per window (inTurn). The backend merges under one lock and writes atomically (tmp + rename, fsync, .bak), and refuses to save over a settings file it could not read.
- Secrets never reach the window: get\_settings and every settings-saved broadcast strip them, the front-end SECRET\_KEYS list matches the backend's SECRET\_SETTINGS exactly, and the backend keeps stored secrets on every write.
- The trust prompt fails safe: with no prompt mounted the answer is Don't run, and unmounting answers every waiting prompt Don't run. Rust re-checks the script fingerprint when the script actually runs, so the prompt cannot be skipped or raced by a script edited after it was shown.
- The update timetable is pure logic over an injected clock and well tested: shared in-flight checks, backoff to 6 h, wake detection, a 45 s timeout. Refused installers have no bypass and no Try again.
- The Warp and Ghostty importers have line caps, a time budget, size caps and a theme-name folder check. Terminal import reads settings back to confirm a save really landed.
- The draft controller (draft.ts) handles IME composition, keystrokes typed during a save and in-order saves carefully. It only falls down at the useSettings wiring.

**Not reviewed in this area:** src/settings/InputCards.tsx; src/settings/SchemePicker.tsx; src/settings/shortcutRows.ts; src/settings/claudeKey.ts; src/settings/writerModels.ts; src/settings/reviewBots.ts; src/settings/fonts.ts; src/settings/pickers.ts; src/settings/searchMore.ts; src/settings/useSearchHits.ts; src/i18n/packs/es.ts, ja.ts, ko.ts, zh-CN.ts (assumed same shape as fr.ts); all other \*.test.ts and \_\_cards\_\_ files in the slice.

## F03-terminal-keys: Terminal panes, keyboard and floating terminal UI

The terminal pane and keyboard code is careful work. Paste, link opening and cleanup on close are defended in depth, and the shortcut layer follows the COMPAT keybindings contract. The weak spots are in how the pieces interact over time: replaying saved output after a restart re-runs live effects (bells, clipboard writes, answers typed into the new shell), a size change while a pane is starting is never sent to the program, and the scrollback limit is reset by unrelated settings saves. The floating panel is the least finished part: its keys fall through to whatever pane is focused in the main window, it stops running programs without the usual 'are you sure?', and its PowerShell tabs probably wait about 4 s for a prompt because the pre-prompt gate holds the console's cursor question. Link click areas are shifted by emoji and CJK characters. Cross-slice notes: the other half of finding 1 is App.tsx's capture-phase key handler, which picks scopes without looking at where the keyboard is; the Rust terminal\_resize is called for every pane on every settings save and holds the registry lock across a service round trip; and the default 'Kolux first' policy deliberately takes Ctrl+L/P/N/W/K/B/T/J from shells and agent CLIs, as documented in TERM-079.

**What is done well:**

- Paste is handled with care: the whole paste is bracketed once, ESC bytes are removed inside brackets, a single line loses its trailing newline so it never runs by itself, pastes of 2+ lines into a program without bracketed paste ask first, an 8 MB cap applies, chunks go in order through one write chain, and Ctrl+C or Esc cancels what is still queued.
- Link opening has several layers of defence: only http, https and file schemes are allowed (checked in TS and in Rust), control characters are refused, Rust refuses UNC hosts and only reveals programs instead of running them, the first plain web click asks where links should open, and the hover hint shows the real target, OSC 8 links included.
- Unmount cleanup is thorough: every window and element listener, interval, observer, IPC listener (including the StrictMode registration race), GPU pool slot, find worker and the PTY itself are released.
- The GPU path is bounded: at most 6 WebGL contexts, the probe gives its own context back, and a lost context falls back to plain drawing.
- The keymap resolver follows the COMPAT 4.1/4.2 file contract closely (older top-level form, platform section precedence, per-id errors, digit-index chords, AltGr guard). The one change from it, custom chords winning over defaults, is recorded in DECISIONS.md as DT-C48.
- Find runs user regexes in a worker with a time budget, and plain search maps wide characters to cells correctly.
- OSC 52 never reads the clipboard back to a program, caps the payload, and ignores writes from hidden panes.

## F04-projects-scm: Projects sidebar, worktrees and source-control UI

This area is careful in its pure rules, and the back-end safety checks are good: discards ask with honest wording, git gets literal paths, links are never followed, and a delete is refused if the workspace changed since the question. - Huge change sets are capped with honest banners (SECTION\_CAP, PANEL\_CAP, the cut-short note with a .gitignore offer), and bulk staging is batched.
- The pure model files (scm/model.ts, rules.ts, projects/cleanup.ts, bulkRemove.ts, menu.ts, deleting.ts) are small, well commented and unit tested.

## F05-app-shell-launch: App shell, launch chooser, status, board and inbox

The app shell is carefully built: effects clean up after themselves, the quit flow waits for the layout save, and most status rules sit in small tested modules. The wiring in App.tsx has several real behaviour bugs. Most visible: every time you return to a workspace with agent tabs, or first open one after a restart, a false 'agent has not started' warning appears, because the start watch forgets panes it already saw. Two problems involve saved state across restarts. A slow start (settings answer over 1.5 s) leaves the window with no tabs and the next click permanently overwrites the saved tabs. Saved agent statuses are matched only by tab number, so new tabs can show an old closed tab's 'needs you' or 'working' state. A multi-agent Start can also hang for good on 'Starting…' if its Setup tab is closed while agents wait for setup. Smaller race and stale-data issues: lost command-line events, failed panes left behind, chooser picks reset after an install, and a 120 ms spinner that re-renders the whole window. One more risk, not listed as a finding: the agent-status listener compares against React-rendered state (hookRef), so two status events for one pane before a re-render could leave a wrong state; this looks rare because the hook server is sequential. Cross-slice notes: the worker-start setup gate has the same never-resolving wait when its Setup tab is closed, and Rust's saved status rows are never pruned when a tab closes (saved.rs).

**What is done well:**

- Effects almost always clean up: Tauri listen/unlisten pairs are released (often with .catch), stale async answers are dropped with live/gone flags, and intervals are cleared.
- The quit path is careful: closing waits for the last layout write, layoutWriter.flush never rejects, so a failed save can never block the window from closing, and unsaved editors or running agents are asked about first.
- Status logic lives in small pure, tested modules (gone.ts, restored.ts, inbox.ts, tower.ts, chip.ts, seats.ts, launchOrder.ts), so the rules are readable and checkable.
- Context readings are decided outside React state updaters (shownRef, held reports with timers), which avoids double-application under Strict Mode.
- Security-sensitive hand-offs are checked on the Rust side: prompt\_answer refuses when the screen no longer shows the answered prompt, open\_external allows only http/https/mailto, and per-launch arguments refuse shell metacharacters (agentstart/rules.ts parseArgs).

**Not reviewed in this area:** All .css files in the slice; Most \*.test.ts and \_\_cards\_\_ files in the slice (only the ones named above were opened); src/carry/settingsRegistry.test.ts; src/board/boardModel.ts after line 125; Rust behaviour behind agent\_start\_line, terminal\_spawn and the hook-to-state mapping (other slices).

## F06-tasks-chat: Tasks and chat views

The Tasks page is GitHub issues and pull requests only; this slice has no local Markdown task files, so there is no file round trip to break. The tasks code is careful: descriptions are drawn safely, edits shown at once settle and roll back correctly, and stale answers are dropped. Its real gap is that saving a description overwrites whatever an agent, bot or teammate changed on GitHub meanwhile, without warning, and a stray click outside the issue dialog throws away an unsaved edit. The chat code's terminal-typing path is solid, but agent-written plans and to-do lists are inserted as live HTML through DOMPurify's default settings, so agent output can restyle or cover the window (including disguising the Allow/Deny card) or add a fake form. The same renderer is used by terminal/PlanSheet.tsx in another slice. Long or unusual transcripts expose measured performance problems: a quadratic email/link regex that can freeze the window on one long encoded string, a message-merging step that costs hundreds of milliseconds per live-preview update in long sessions, and @-file ranking that lags in very large repositories. Cross-slice notes: chat\_tools.rs checklist() does not escape to-do text, and scm/review.ts pastes CI logs into the agent prompt unframed, an inherent prompt-injection channel for pull requests from forks.

**What is done well:**

- GitHub issue and PR descriptions and comments are drawn by src/tasks/markdown.ts plus MarkdownView.tsx as React elements, never as HTML. Only http(s) links are kept, and unclosed HTML comments cannot hide the rest of a description.
- Edits shown at once in Tasks (edits.ts) are kept as additions and removals over GitHub's rows, settle when GitHub agrees, expire, and roll back only themselves on failure. Label and assignee edits everywhere are sent as add/remove diffs, so they never clobber someone else's labels.
- Stale answers are dropped carefully throughout: a sequence counter on Tasks searches, `live` flags on effects, epochs and turn counters in ChatReader, close-before-read ordering, and per-cell edit book-keeping in ProjectsView so a late reply never overwrites a newer edit.
- Typing into an agent's terminal is defensive. harmless() strips ESC and C1 control characters, so an end-of-paste marker cannot be smuggled in. Text goes in as a bracketed paste. The pane's hook state is re-checked before every write, including the Enter. Stop cancels queued sends and uses Escape only.
- Merging from the PR page needs an explicit confirm, is pinned to the head commit shown, and the confirm closes when new commits arrive.
- Chat file links open only paths the agent itself printed recently and go to the editor (App.tsx wires onOpenFile). mailto links lose cc/bcc/attach parameters, and web links have no href to middle-click around the browser choice.
- The chat agent support table is consistent: src/chat/model.ts CHAT\_AGENTS matches chat.rs SUPPORTED (claude, openclaude, codex, omp). The permission card leaves out OpenClaude because its keys are unconfirmed.
- All tests in this slice pass on Linux (the one vitest failure is chrome/STAT-052, outside the slice).

**Not reviewed in this area:** src/tasks/RoadmapTimeline.tsx (grep only); src/chat/ModelControls.tsx (grep only); src/tasks/fakeDom.ts; src/tasks/tasks.css; Most \*.test.ts and \_\_cards\_\_ tests in the slice (used only to check coverage of suspected bugs); Rust orchestration send path behind scm\_review\_send / cli.rs terminal.send (other slice).

### F06-tasks-chat.3 A long unbroken run of letters and digits in an agent reply freezes the chat view (quadratic link and email regexes)

- **Severity after checks:** medium · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** performance
- **Where:** `src/chat/chatLinks.ts:19`
- **What you would notice:** If an agent's reply contains a very long encoded string, the whole Kolux window freezes for seconds at a time while that conversation is on screen.
- **How it happens:** partsOf runs on every assistant reply. ChatText runs it on every render of every visible reply row (ChatView.tsx:373; rows are not memoized, and ChatView re-renders on each transcript read and hook event), and printedPaths runs it again over the last 200 items on every items change (ChatView.tsx:183, chatLinks.ts:116). Add a timing test like TERM-095's (for example, 40 KiB of 'x' under a few ms).
- **Reviewer (confirmed, medium):** EMAIL (chatLinks.ts:19) has no run-start guard, unlike the TERM-095 lookbehinds in terminal/links.ts:15-27. ## X-sec: Security architecture across the whole app

> Note from the report: this auditor took it that Tauri's command bridge loads only into a page's top frame. Two other auditors (L1-tauri.1 and R07-browser.1) traced the Windows web engine and found it is added to every frame; see item 3 of the report. A live test on Windows settles it.

The app's outer walls are strong. Web pages in the built-in browser cannot reach app commands. The main window cannot be taken over by an outside page, the content policy is strict, the local servers for agent hooks, the command line and the terminal service check tokens and refuse web-page requests, and saved keys are encrypted and kept away from the window. The most serious weakness is how Kolux starts agents installed through npm on Windows (Gemini CLI, OpenCode, Pi and others that Kolux itself installs this way). The opening prompt passes through cmd.exe without proper escaping, so a GitHub issue or pull request title written by a stranger can make Windows run an extra command when you click 'Start with an agent', and ordinary prompts with quotes or symbols can break. Kolux also pre-answers Claude Code's and Codex's 'Do you trust this folder?' question for every worktree it makes, including checkouts of other people's pull requests, which lets that repository's agent settings run without a warning. The document-preview server guards files with a predictable token and no Host check, and Markdown from agents can restyle the window. No real API keys or private keys are committed; only your Windows user path appears in proof scripts and evidence.

**What is done well:**

- Tauri 2.12.1 refuses app commands from any non-local page unless a remote capability exists, and none is granted (webview/mod.rs:2080). Tauri's IPC scripts load only into the top frame.
- Browser tabs can never navigate to \*.localhost or the app's own origin (browser.rs:1104-1118, checked on navigation, pop-ups and opens). The artifact scheme answers only the main webview (lib.rs:466-470), and artifact pages run in an iframe sandboxed without allow-same-origin.
- The main window's navigation guard sends every outside address to the system browser, so no page can take over the Kolux window (tools.rs:415-440, menu.rs:303-323).
- Strict CSP (script-src 'self', object-src 'none'), covered by scripts/csp.test.mjs. No withGlobalTauri, no devtools feature, no asset protocol.
- The hook endpoint drops web-page requests (Origin, Referer, Sec-Fetch), checks Host against DNS rebinding and needs a random token (hooks.rs:332-344). The CLI server drops HTTP request lines. The terminal service needs a token in its first message.
- The updater fails closed without a built-in signing key and uses an https GitHub feed (update.rs:29-69). The installer hooks only print a line.
- Secrets are sealed with DPAPI and never sent to the page (lib.rs:132-135, secrets.rs). The profile folder is limited to the user. Secret environment variables go only to the matching agent's panes.
- Link and file opening is defensive: open\_external allows only http, https and mailto, with a rate limit. open\_path shows program-like files in their folder instead of running them, and refuses UNC, device and control-character paths (links.rs).
- Mermaid runs with securityLevel strict inside a sandboxed srcdoc iframe. KaTeX runs with trust:false and is sanitised.
- Repository-supplied kolux.yaml scripts need a trust grant that Rust enforces (setup.rs:303-305). The skills installer refuses cmd.exe syntax characters (skills/installer.rs:132-145).
- Approving a self-signed certificate is limited to loopback sites and to actions the app itself starts (browser\_certs.rs).

**Not reviewed in this area:** Most of the ~420 Tauri commands individually: only file and open commands were spot-checked; browser\_cli.rs agent browser driver and browser\_engine.rs WebView2 event wiring; browser\_cookies.rs cookie import from real browsers; claude\_accounts.rs, codex\_accounts.rs, grok.rs sign-in and credential flows; agent\_hooks vendor normalizers and the spool replay; orchestration and the kolux CLI dispatch commands; protected-command rules (SAFE-009) logic; diag.rs scrubbing completeness and crash bundles; macOS and Linux runtime behaviour; git history (excluded by the clean-room rules).

### X-sec.1 Opening prompts reach cmd.exe unescaped when an agent is an npm .cmd shim (text from GitHub issues, PR titles and check names included)

- **Severity after checks:** high · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** security
- **Where:** `src-tauri/src/pty.rs:344`
- **What you would notice:** If you click 'Start with an agent' on a GitHub issue or pull request whose title a stranger wrote, Windows can run a command of that stranger's choosing on your computer. Even your own prompts that contain quotes and symbols like &amp; or % can start the agent with a cut-off or changed prompt.
- **How it happens:** Kolux installs Gemini CLI, OpenCode, OpenClaude, Pi and Command Code through npm (agent\_install.rs:110,122,128,155,189). On Windows that makes them .cmd shims, and find\_program resolves them to those shims (agents.rs:132-154). These agents take the opening prompt as a plain argument (agents.rs:385-391, 557-561). start\_line runs every shim as `cmd.exe /d /c <shim> <args>`. portable-pty builds the command line with C-runtime quoting only (backslash before a double quote, cmdbuilder.rs:702-743), and cmd.exe does not understand that quoting. A prompt that contains double quotes therefore shifts what cmd.exe treats as quoted, and shell control characters after that point are read as command separators or redirections. The prompt is untrusted in common flows. 'Start with an agent' on an issue or pull request puts the item's GitHub title into the prompt (agentstart/fromItem.ts:18-24), and anyone can open an issue or pull request on a public repository. The failing-checks fix puts check names and descriptions into the prompt (fixChecks.ts:15-21), and a fork's own workflow sets those. Worker prompts sent by another agent through the kolux command line take the same path (App.tsx:1775, 1791). So a stranger's text can make cmd.exe run an extra command as the user, outside any agent sandbox. No Rust code escapes or refuses these characters (terminal\_spawn, terminal.rs:1734 onward). Ordinary prompts break too: quotes combined with &amp;, |, &lt; or &gt; cut the prompt short, %NAME% is silently expanded, and when the shim folder has a space (a Windows user name with a space) any multi-word prompt makes the start fail, which the ponytail note at pty.rs:333-335 only half describes. The authors handled this for session ids only (agents.rs:421-428, safe\_session). Severity: rated high rather than critical because it needs a user click and an npm-installed agent, but the text comes from strangers.
- **Code:** `if shim { ("cmd.exe".into(), vec!["/d".into(), "/c".into(), resolved.as_os_str().to_owned()]) // program_command then does cmd.args(args) with the prompt as one argument (pty.rs:320-329)`

For a .cmd/.bat shim, either start the shim's real target directly (node.exe plus the package script that the npm shim names), or use the pattern skills/installer.rs:132-145 already uses: one `cmd.exe /d /s /c "..."` line that refuses or caret-escapes every argument containing " &amp; | &lt; &gt; ^ % ! or a newline. The simplest safe choice is to hand the opening prompt to shim-launched agents by the typed route (Route::Typed, SESS-032) instead of as an argument. Add tests with quotes, &amp;, %VAR% and a shim path that contains a space.
- **Reviewer (confirmed, high):** I followed the real code from the button click to CreateProcessW and found nothing on the path that escapes or refuses cmd.exe syntax in the prompt. Path: 1. The title comes raw from the GitHub API. 2. runFromItem checks only the per-launch arguments (parseArgs), then makes the workspace. For an issue, the branch name is cleaned with safe\_name and falls back to "workspace", so a title containing &amp; does not stop it. 3. (shortened)
- **Reviewer (confirmed, high):** I traced the path end to end in the code. I did not run it on Windows. ### X-sec.3 Document-preview server uses a predictable path hash as its access token and does not check the Host header

- **Severity after checks:** low (the auditor said medium) · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** security
- **Where:** `src-tauri/src/browser_preview.rs:55`
- **What you would notice:** A website or another account's program that guesses where your project lives may be able to read files from a folder you previewed and allowed, such as a .env file with passwords.
- **How it happens:** The user previews docs/index.html from a project folder in a browser tab and presses Allow folder so the page's styles and scripts load (BROW-040). Until the window reloads, http://127.0.0.1:&lt;port&gt;/&lt;token&gt;/... serves every file in that folder, including .env files and .git/config. The token is DefaultHasher::new(), which is SipHash with fixed zero keys, applied to the lower-cased folder path. It is the same on every run, so anyone who can guess the path can compute it. serve() (browser\_preview.rs:233-255) accepts any GET without looking at Host, Origin or Sec-Fetch headers, unlike the hook endpoint's gate (hooks.rs:332-344), and there are no rebinding or Host tests (tests at 450-602). Another Windows user on the same machine can scan the loopback ports and read the files. So can a web page in a browser without local-network protection, using DNS rebinding. All previews also share one origin, so a previewed page from one repository can fetch another previewed folder's files if it can guess that folder's path. Exploitation needs the port and the path, so it is not easy, but the token gives none of the protection its name suggests.
- **Code:** `fn token_of(root: &Path) -> String { let mut h = std::collections::hash_map::DefaultHasher::new(); root.to_string_lossy().to_lowercase().hash(&mut h); format!("{:016x}", h.finish())`
- **Suggested fix:** Give each preview a random token from crate::cli::secret(), kept in memory only. Reject requests whose Host is not 127.0.0.1:&lt;port&gt; or that carry cross-site Sec-Fetch-Site or Origin headers, reusing hooks::gate's logic. Consider one port (one origin) per previewed folder. Add tests for a wrong Host and a guessed token.
- **Reviewer (confirmed, low):** The code facts hold. token\_of hashes the lower-cased canonical folder path with DefaultHasher::new() (browser\_preview.rs:55-59). Rust documents every hasher created through new as the same, with no per-process random key, so the token is a fixed, computable function of the path. serve() reads only the request line and never checks Host, Origin or Sec-Fetch (browser\_preview.rs:233-248), unlike hooks::gate (hooks.rs:328-344). (shortened)

### L2-rust-crates.4 fetch\_script buffers the whole HTTP body before enforcing the size cap when Content-Length is absent

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** resource-leak
- **Where:** `src-tauri/src/artifacts.rs:269`
- **What you would notice:** If one of the trusted script servers were compromised, fetching an offline-artifact script could make the app use up all memory and crash.

### L3-terminal-editor-js.2 Terminal link underlines and click areas use string positions as screen columns, so links after CJK text are misplaced and wrapped ones get cut

- **Severity after checks:** medium · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** bug
- **Where:** `src/terminal/links.ts:137`
- **What you would notice:** In a terminal, a web address or file path that comes after Chinese, Japanese or Korean text is underlined in the wrong place, and if it wraps onto the next line Ctrl+click can open a cut-off, wrong address.
- **How it happens:** xterm's ILink.range is in buffer cells (IBufferCellPosition). translateToString emits one JS character for a 2-cell CJK character (xterm BufferLine.ts:524-550: it advances startCol by the cell width but appends one char). spanOf pads each wrapped row to `cols` string characters and rangeOf maps a string index straight to a column. ## Refuted findings

These were reported by an auditor and then shown not to hold. They are kept so nobody reports them again.

- **F04-projects-scm.8: Starting a second workspace cancels a first one still being created, in any project, and the first prompt typed for it is gone** (`src/projects/model.ts:151`). This is the specified behaviour. PROJ-020 says 'a creation overtaken by a newer one is cancelled and its half-made checkout removed' (spec/01-projects-worktrees.md:71-72), and only Create more exempts a create (:81-83; T-013-c, PLAN-done.md:49). The rule is not limited to one project. ProjectsPanel.tsx:813-817 documents exactly this, and overtakenBy (model.ts:149-152) and the cancel loop (ProjectsPanel.tsx:836-840) implement it as written. The user is told 'cancelled: a newer workspace creation took its place' (projects.rs:892, ProjectsPanel.tsx:889). Clearing the form on submit (:842-846) is normal. (shortened)
- **F08-onboarding-look-misc.3: The 'First steps … All done' box stays in the sidebar for good, cannot be hidden, and keeps the Getting Started entry from ever showing** (`src/onboarding/newcomer.ts:41`). SidebarStart, the only component that renders the compact Checklist (SidebarStart.tsx:29), is imported nowhere in the app except sidebarStart.test.ts. ProjectsPanel.tsx imports HelpMenu (line 72) but not SidebarStart, and no other file renders &lt;Checklist&gt; or the onb-checklist markup. The mount sits in the held coordinator patch evidence/accounts-FIX-3-sidebar.patch (PLAN-done.md T-295: 'mount held ... so no user sees the entry before then'). So at this commit no 'First steps / All done' box ever appears. The sidebar Getting Started entry is also unmounted, and Getting Started is still reachable from the Help menu (HelpMenu.tsx:37). (shortened)
- **X-sec.2: Kolux pre-accepts Claude Code's and Codex's folder-trust warning for worktrees that hold other people's code (fork pull requests, newly cloned repositories)** (`src-tauri/src/trust.rs:154`). The mechanics are accurate. workspace\_open\_pr records a fork pull-request checkout as madeBy "app" (projects.rs:1388-1403). openIn calls pretrust before every start (App.tsx:1379, 1804-1808). trust\_for\_launch then writes hasTrustDialogAccepted or trust\_level for any folder with an origin record (trust.rs:154, 206, 229-249), and nothing excludes cross-repository PRs. This is the specified design, though, as the finding itself admits. SAFE-023 requires every freshly made worktree to be recorded as trusted in the agent's own config before launch (spec/10-plan-review-protected.md:25-43). GIT-049 explicitly starts agents in fork-PR worktrees (spec/11-git-review.md:744-750). (shortened)
- **L1-tauri.3: Sign-in pop-up windows are created already loading their page, which WebView2 does not allow for the opener's new window** (`src-tauri/src/browser_popup.rs:156`). The code facts are right. browser\_popup.rs:156 builds the pop-up with the requested URL. tauri-runtime-wry lib.rs:4747 navigates any URL that is not about:blank, and wry navigates at creation (webview2/mod.rs:597), then calls SetNewWindow and ignores the result (:840). Tauri's own examples use about:blank (webview/mod.rs:568, webview\_window.rs:294). The claimed effect, however, is contradicted by the repo's own live WebView2 run of this same code; the line is unchanged since the 2026-10-27 root commit. In evidence/browser-954b.txt (live re-proof, 2026-10-28), items 1a and 1c PASS. (shortened)
