Each entry carries enough detail for whoever fixes it; the report is the place to start.

**How each finding was checked.** One auditor read each area and wrote findings. Every finding the auditor rated critical or high then went to two separate reviewers told to refute it: one traced the actual code path, the other asked whether it can really happen in the shipped Windows app and whether the spec meant it. Findings rated medium went to one reviewer, in batches of up to six. Findings rated low were not double-checked. When reviewers disagreed on how serious a finding is, "Severity after checks" is the lowest rating from any reviewer who agreed it was real. Refuted findings are listed at the end of the front-end file so nobody reports them again. IDs such as `R01-cli.2` follow each auditor's own numbering, so the list below is sorted by severity but the numbers are not always in order.

**Totals for the whole audit.** 194 findings from 25 code, security, process, test and library auditors. By check: 104 confirmed, 85 unverified, 1 uncertain, 4 refuted. Severity after checks, refuted ones left out: 12 high, 73 medium, 105 low.

Probe scripts and logs the auditors used existed only during the audit; they appear as "an audit test file" or "the audit's own check log".

**Words used here.** Worktree: the separate folder git makes for each Kolux workspace. CI: GitHub's automatic build-and-test run. Hook: the small script an agent runs to tell Kolux its status and to ask before a risky command. npm: the Node.js package installer. cmd.exe: the old Windows command prompt. Lock: while one part of Kolux holds it, every other part that needs the same data waits.

## R01-cli: The kolux / kolux-dev command line and the loopback server it talks to

The kolux command line is large and well defended at the network edge: the loopback port needs a random token, web pages are turned away, file commands stay inside the worktree, and errors are clear and consistent. The most serious problem is outside the server: on an installed Windows copy, registering the kolux command (setup guide and Settings) looks in the app's folder instead of its bin folder, so it always fails. The server answers one request at a time and holds the app's main data lock while running git for every project, so one slow command (starting a worker, waiting on a page, a download) or a long project list stalls every agent and can make the window stutter. A single oversized --wait-submit value crashes the whole app, because release builds abort on any panic. Several command words and flags have drifted from COMPAT.md (tab profile commands, automations --base-branch and runs, reset --retry-request), and smaller slips break documented commands: screenshot --format, viewport --mobile, relative upload paths, and worktree list failing when one project is missing. Cross-slice: onboarding.rs cli\_status has the same bin-folder bug, and pty\_service::launch\_detached inherits the same working-folder problem as kolux open.

**What is done well:**

- Loopback-only server: it listens on 127.0.0.1 on a random port and checks a 128-bit token from OS randomness on every request, including the quick status answer given while another request runs.
- Web pages are shut out: HTTP request lines are dropped unanswered, so a malicious page or DNS rebinding cannot drive the command port.
- Clear error model: the CLI-004 envelope separates app\_unreachable, lost\_result, timeout and version\_gap, and errors carry hints and next steps.
- Long waits (check --wait, ask, terminal wait) poll from the client in short requests, and ask hands control back before agents' 2-minute tool limit.
- File commands (file open/diff) keep paths inside the worktree both by spelling and through links; the worktree check in file\_cli::inside is sound.
- Caller identity is tied to a per-pane key, so --from cannot pretend to be another terminal (orchestration::caller\_of).
- Orchestration changes get lasting UUID retry ids, saved receipts and request-show, so a lost answer can be finished without doing the change twice.
- Windows PATH registration reads PATH back after writing, keeps the variable's existing name and expandable type, and never removes entries it did not add. The macOS administrator command is quoted carefully.
- The parser has extensive unit tests for typo suggestions, help paths and refusals.

**Not reviewed in this area:** src-tauri/src/cli.rs lines 2470-2690 (layouts, ps internals, overlap); src-tauri/src/cli.rs lines 3000-3370 (rest of mail(): dispatch, task, gate and reset handlers); src-tauri/src/cli.rs lines 3640-3727 and 3940-4300 (dispatch stamps, late notes, release\_worker, worker stop/abandon/retain); src-tauri/src/browser\_cli.rs lines 1125-1525 (tab, lease and profile handlers, text output, the DRIVER page script); src-tauri/src/automations\_cli.rs lines 240-368 (create/edit/run bodies); All #\[cfg(test)\] modules, apart from spot checks for coverage; src-tauri/tests/\*.rs integration tests other than shim.rs.

### R01-cli.1 Registering the kolux command looks in the app's folder, but the installed copy keeps kolux.exe in bin\

- **Severity after checks:** high · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** bug
- **Where:** `src-tauri/src/cli_register.rs:508`
- **What you would notice:** On an installed copy, the button that makes the kolux command work in every terminal always fails, so agents started outside Kolux can never use kolux.
- **How it happens:** The release build ships the CLI as bin/kolux.exe and bin/kolux.cmd (scripts/release.mjs:220-221, DECISIONS DT-R27). installer-hooks.nsh adds nothing to PATH, so cli\_register is the only way to put kolux on PATH. A user on an installed Windows copy opens the Setup Guide CLI step (src/onboarding/CliSetup.tsx:51) or Settings &gt; CLI and clicks Register. folder\_and\_exe() returns the install folder (the folder of kolux-rs.exe), and command\_file() finds no kolux.exe or kolux.cmd there (cli\_register.rs:513-519). The call fails with '...holds no kolux.exe or kolux.cmd, so there is nothing to register'. cli\_register\_state, windows\_register and windows\_remove all check that same wrong folder, and even a successful write would put the wrong folder on PATH. Cross-slice: onboarding.rs:551-553 cli\_status makes the same mistake, so it returns installed:false; the 'Kolux CLI' capability (src/onboarding/guide.ts:68) and the CLI tip (guide.ts:156) can never complete. terminal.rs:1004-1006 and launch\_app (cli.rs:1139-1146) already handle the bin folder correctly. No test covers the bin layout, and PLAN marks T-250-b/c 'live proof pending'.
- **Code:** `let dir = exe.parent().map(Path::to_path_buf).ok_or("Kolux cannot find its own folder")?; ... Err(format!("{} holds no {name}.exe or {name}.cmd, so there is nothing to register", dir.display()))`
- **Suggested fix:** Write one shared helper that picks &lt;exe folder&gt;\bin when it holds kolux.exe (the same rule as terminal.rs:1004-1006). Use it in cli\_register (state, register, remove) and in onboarding::cli\_status. Add a test with a temporary folder laid out like the install.
- **Reviewer (confirmed, high):** I followed the code from the installed file layout through to the error. 1. \*\*Install layout.\*\* - scripts/release.mjs:221 maps src-tauri/cli/kolux.cmd to "bin/kolux.cmd" and target/release/kolux.exe to "bin/kolux.exe" as bundle resources. - On Windows, Tauri's resource dir is the exe's own folder (tauri-utils platform.rs:305-309). - When a map entry is a single file, its target is exactly the mapped value (tauri-utils resources.rs, `dest.clone()`). (shortened)
- **Reviewer (confirmed, high):** I tried to refute the finding on reachability, other layers, intent and severity. None of these refutes it. 1. Install layout. scripts/release.mjs ships the CLI only as Tauri resources mapped to bin/kolux.cmd and bin/kolux.exe. In the NSIS template inside the installed @tauri-apps/cli 2.12.1 binary, the main exe and the resources (`/oname=<target>`) are written under `SetOutPath $INSTDIR`. tauri-utils `resource_dir` on Windows is the exe folder. So the CLI ends up at &lt;install&gt;\bin\kolux.exe. 2. No second copy beside the app. (shortened)

### R01-cli.2 One slow kolux command stalls every agent's kolux calls, and calls abandoned in the meantime still run later

- **Severity after checks:** medium · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** reliability
- **Where:** `src-tauri/src/cli.rs:4880`
- **What you would notice:** While one agent starts a worker or waits on a web page, every other agent's kolux commands hang for minutes, and commands they retried can then happen twice.
- **How it happens:** The app answers kolux requests strictly one at a time (serve\_loop\_with, cli.rs:4879-4936), and several handlers wait inside that single loop. orchestration worker-start waits up to 200 s for the window's setup gate (orchestration/setup\_gate.rs:16) and then 60 s by default for the worker (cli.rs:3809, 4788). Its --timeout-ms has no upper limit (check\_worker\_start only refuses 0, cli.rs:818-822). 'kolux wait --timeout' can run 300 s (browser\_cli.rs:160), 'kolux download' 120 s (browser\_cli.rs:1087), and 'terminal send --wait-submit N' has no limit (cli.rs:3487-3491, 3546). Example: a coordinator starts a worker whose setup runs npm install. Meanwhile every other agent's 'kolux terminal read', 'orchestration send' and browser command waits in the queue. Agents' shell tools give up after about 2 minutes (the code itself notes this at cli.rs:1488) and kill the kolux process. Nothing checks whether a queued request's caller is gone or how old the request is, so it still runs once the queue drains. An agent that retried 'kolux terminal send --text yes --enter' gets the text typed twice, because terminal send gets no automatic retry id (CHANGES at cli.rs:173 covers orchestration only). This is a recorded ponytail, but it hurts the app's core many-agents use. check --wait, ask and terminal wait already poll from the client side (cli.rs:1518-1580), which is the right pattern.
- **Code:** `// ponytail: one request at a time; a parallel accept loop if agents ever queue up on it. ... for (mut stream, arrived, line) in taken { ... let out = handle(&Request { arrived: Some(arrived), ..req });`
- **Suggested fix:** Move long waits out of the serve loop: poll from the client the way check --wait does, or run requests on worker threads with locks per resource. Cap --timeout-ms and --wait-submit. Before running a queued request, skip it if its connection has closed or if it is older than CALL\_WAIT.
- **Reviewer (confirmed, medium):** serve\_loop\_with (cli.rs:4879-4936) runs every request through `handle` on a single thread. dispatch calls the long waits inline: worker\_start\_once/join\_running (cli.rs:4357-4431) waits up to setup\_gate::LIMIT of 200 s (setup\_gate.rs:16) and then wait\_ready for DEFAULT\_TIMEOUT 60 s, or any --timeout-ms (cli.rs:818-822, 4676). browser wait can run up to WAIT\_MAX\_MS 300 s (browser\_cli.rs:160, 551-575), download up to 120 s (browser\_cli.rs:1087), and --wait-submit has no cap (cli.rs:3546-3550). (shortened)

### R01-cli.3 CLI worktree lookups hold the app's main data lock while running git once per project

- **Severity after checks:** medium · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** performance
- **Where:** `src-tauri/src/cli.rs:1982`
- **What you would notice:** While agents use kolux, especially the browser commands, the Kolux window can stutter or freeze, for a long time if a project sits on a slow drive.
- **How it happens:** Several lookups keep the Store lock held while list\_workspaces runs 'git worktree list --porcelain' for every project (git.rs:661-663, with a 30 s timeout at git.rs:484). They are pick\_in (cli.rs:1977-2010), pick\_project (1925-1956), calling\_worktree (1961-1966), terminal\_rows (2280-2286), worktree list (2735-2740) and set\_worktree (2065). Every browser command given without --worktree calls pick\_worktree("current") (cli.rs:2244), so an agent driving the browser scans all projects under the lock on every click. The window's own path deliberately lets go of the Store while git runs (projects.rs:1602-1619, T-442/TERM-115). 82 non-async Tauri commands take the Store (for example project\_list at projects.rs:1555-1559), and non-async commands run on the window's thread (the agent\_list\_command.rs header says so). With about 10 projects at roughly 50-150 ms per git start on Windows, each lookup can stall the window for about a second. A project on a slow or offline network share can add up to 30 s per project.
- **Code:** `let store = ctx.store.lock().map_err(|e| e.to_string())?; ... for p in projects::load_projects(&store) { for w in projects::list_workspaces(ctx.git, &store, &p).unwrap_or_default() {`
- **Suggested fix:** Follow projects::scan: copy the project list under the lock, release it, run git, then lock again only for the store reads. Optionally cache worktree lists briefly for selector lookups.
- **Reviewer (confirmed, medium):** pick\_in (cli.rs:1977-2010), pick\_project (1928-1956), calling\_worktree (1961-1966), terminal\_rows (2280-2287) and worktree.list (2735-2741) all keep `ctx.store.lock()` held while list\_workspaces runs `git worktree list --porcelain` for each project (projects.rs:488-495, git.rs:661-663, READ\_TIMEOUT 30 s at git.rs:484). The browser arm calls pick\_worktree("current") on every browser command given without --worktree (cli.rs:2251-2255), and that scans every project. The window's own scan() releases the lock before running git (projects.rs:1606-1619). (shortened)

### R01-cli.4 `kolux open` starts Kolux inside the caller's folder, which Windows then refuses to delete or rename

- **Severity after checks:** medium · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** cross-platform
- **Where:** `src-tauri/src/cli.rs:1149`
- **What you would notice:** If Kolux was started with kolux open from inside a worktree, you can't delete or rename that worktree until Kolux and its background terminal service are fully stopped.
- **How it happens:** When Kolux is closed, every kolux error tells the caller to run 'kolux open' (cli.rs:862-863), so an agent working in a worktree runs it from that folder. launch\_app (cli.rs:1135-1158) starts kolux-rs.exe without setting a working folder, and the app never changes its own (there is no set\_current\_dir anywhere). In release builds the app then starts the background terminal service the same way (pty\_service.rs:707-721, terminal.rs:1503-1516), and that service keeps running after the app quits. Windows will not rename or remove a folder that is any process's working folder. Removing that worktree later (worktree\_remove first moves the folder to a trash, git.rs:691-694 and 342-353) fails with '...nothing was deleted: close the programs that have files open in the folder'. The program holding the folder is Kolux itself, and quitting Kolux is not enough while the terminal service runs. Not reproduced here: Windows behaviour, judged from the code.
- **Code:** `let mut cmd = std::process::Command::new(&exe); cmd.stdin(std::process::Stdio::null()).stdout(std::process::Stdio::null()).stderr(std::process::Stdio::null()); // no current_dir(...) before cmd.spawn()`
- **Suggested fix:** Set current\_dir to a neutral folder (the program's own folder or the user's home) in launch\_app and in pty\_service::launch\_detached, or call set\_current\_dir early when the app starts.
- **Reviewer (confirmed, medium):** launch\_app (cli.rs:1135-1158) builds the Command with no current\_dir, so kolux-rs.exe inherits the caller's folder. A grep finds no set\_current\_dir anywhere in src-tauri (only string matches in protected.rs). In release builds, use\_service (terminal.rs:1503-1516) starts the background service through launch\_detached (pty\_service.rs:707-721), also with no current\_dir, so the long-lived service inherits the same folder. (shortened)

### R01-cli.5 A huge --wait-submit number crashes the whole Kolux app

- **Severity after checks:** low (the auditor said medium) · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** reliability
- **Where:** `src-tauri/src/cli.rs:3398`
- **What you would notice:** One mistyped or malicious kolux command from any agent can crash the whole Kolux window.
- **How it happens:** --wait-submit accepts any 64-bit number: parse() refuses only 0 (cli.rs:668-670) and the app's num() takes any u64 (cli.rs:3487-3491). Example: 'kolux terminal send --terminal term-2 --enter --wait-submit 18446744073709551615' on a live terminal. Because Enter plus --wait-submit turns on watching (cli.rs:3577-3579), the request reaches submit\_verdict. There, adding the duration to Instant overflows and panics ('overflow when adding duration to instant'). The release profile sets panic = "abort" (Cargo.toml:80), so a panic on the CLI thread ends the whole app process, window included. Any agent, including a prompt-injected one, can do this with one command. The other waits fed by request values are capped or clamped (browser wait\_limit, worker\_read paging), so this is the one found.
- **Code:** `let start = Instant::now(); let until = start + watch;`
- **Suggested fix:** Cap --wait-submit (and worker-start --timeout-ms) at a sensible maximum when parsing. In submit\_verdict, use Instant::checked\_add with a fallback.
- **Reviewer (confirmed, low):** The client refuses only 0 (cli.rs:680-682), and the app's num() takes any u64 (cli.rs:3487-3491, 3546-3550). With --enter, `watching` becomes true (cli.rs:3578), the call reaches submit\_verdict, and line 3398 computes `start + watch`. std's Instant + Duration panics with 'overflow when adding duration to instant', and the release profile sets panic = "abort" (Cargo.toml:80), so the whole app process ends. The bug is real, but I lowered it because only a deliberately absurd value triggers it. (shortened)

### R01-cli.7 kolux upload and tab create read relative file paths from Kolux's own folder, not the agent's

- **Suggested fix:** Join relative paths onto req.cwd before reading, as repo add already does (cli.rs:2695), both in files\_of and before preview::is\_document/add.
- **Reviewer (confirmed, low):** files\_of (browser\_cli.rs:647-664) reads `Path::new(p)` as given. The client check returns the flags unchanged (browser\_cli.rs:431), and wsl\_fixed rewrites only worktree, parentWorktree and repo (cli.rs:2098-2112). ### R01-cli.9 screenshot --format and viewport --mobile cannot be used as the help documents them

### R01-cli.10 The command port reads requests with no size cap or overall time limit on a single accept thread

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** security
- **Where:** `src-tauri/src/cli.rs:4891`
- **What you would notice:** Another program on the same computer could stall Kolux's command line or make Kolux run out of memory, without knowing Kolux's secret token.
- **How it happens:** Before any token check, one accept thread reads each connection's first line, and the only limit is a 1.5 s timeout on each separate read. ## R02-hooks-status: Agent status hooks and the status state machine

The hooks and status area is carefully built: settings files are changed only through compare-then-rename writes with checksummed backups, removal gives files back byte for byte, and the local endpoint refuses web pages and token-less requests. The biggest risk is the hook Kolux installs for Antigravity: outside a Kolux pane, or when Kolux is slow or closed, it gives no answer. A live-tested third-party library reports that Antigravity then blocks the tool call, which could make Antigravity unusable outside Kolux. The Amp plugin has a similar unverified gap: it returns nothing where Amp's docs and Kolux's own COMPAT.md call for an 'allow'. Inside Kolux, a helper agent whose stop event never arrives (likely after Esc) leaves a pane stuck on 'working'. The single-threaded hook listener can be frozen by any slow local client. A Claude settings file with an empty hook list can never get hooks. The rest are low-impact restore and edge cases. Cross-slice notes: cli::secret() makes tokens from std RandomState hashes rather than a cryptographic RNG; terminal.rs installs Codex hooks at pane start checking only the global switch, not the per-agent off list. Evidence sources used: Antigravity hooks docs (https://antigravity.google/docs/hooks), safe-chains agy notes (https://docs.rs/safe-chains/latest/src/safe\_chains/targets/agy.rs.html), Amp plugin API (https://ampcode.com/manual/plugin-api), Claude Code hooks reference (https://code.claude.com/docs/en/hooks), Cursor hooks docs (https://cursor.com/docs/agent/hooks). Checkpoint notes and scratch experiments are in an audit test file and an audit test file

**What is done well:**

- Settings edits are defensive: every rewrite goes through write\_atomic, which re-reads the file and refuses if the agent saved it meanwhile, then renames a synced temp file. The Claude install also self-checks that nothing but Kolux's entries changed.
- Backups with sha256 records are made before the first write and verified on every install. Removal writes the kept copy's exact bytes when the content matches, and files Kolux created are deleted again.
- Commented and non-JSON formats are edited as marked text blocks (JSONC for Devin, TOML for Kimi, YAML for Hermes with checksums). Removal gives the file back byte for byte, and odd shapes are refused rather than guessed.
- The local endpoint refuses anything a browser would send (Origin/Referer/Sec-Fetch), foreign Host headers (DNS rebinding) and requests without the token, with an empty 404. Tested in tests/cards\_13.rs.
- Hooks are off by default (T-152-gate) and only installed for detected, switched-on agents. Test, dev and lane runs are fenced to scratch folders and cannot touch the user's real files.
- Hook scripts exit before reading stdin outside a Kolux pane. The spool keeps only whitelisted names, never tool input, prompts or replies. Windows read-only files are refused cleanly (std rename fails, std unlink removes the read-only temp file).
- The status state machine guards hard races: late hooks from ended terminals are dropped under the same lock that retires them, cancels have a grace period, denies park and restore children, and the test suite is extensive.

**Not reviewed in this area:** src-tauri/src/agent\_hooks/tests.rs (2540 lines); src-tauri/src/agent\_hooks/more\_tests.rs; src-tauri/src/agent\_hooks/hermes\_tests.rs; src-tauri/src/activity.rs tests (lines 460-923); src-tauri/src/agent\_hooks/grok.rs tests (lines 365-531); No live check of any agent (Antigravity, Amp, Pi, Claude interrupt behaviour); the more.com / code-page path in the batch script on non-Western Windows code pages was not verified.

### R02-hooks-status.3 Hook listener handles one connection at a time with no overall deadline or size cap, so one slow or endless local client freezes every pane's status

- **Severity after checks:** low (the auditor said medium) · **Check:** confirmed (every reviewer agreed it is real) · **Kind:** reliability

## R03-safety-accounts: Safety rules, file fences, secrets and accounts

The safety-rules area is built carefully but has one serious hole. The command splitter that every built-in protected rule relies on misreads ordinary shell text: an apostrophe in a comment, a heredoc or a PowerShell here-string, or an escaped quote, hides the rest of the command. Force-push to main, hard reset and folder deletes then run without the Kolux pause, and since Kolux starts Claude in auto permission mode by default, that pause matters (confirmed by running the exact code). A second, independent way to lose the ask: masking a large paused command is quadratic and happens before the reply, so past about 1.5 s the hook gives up and the command runs; the one-at-a-time listener also stalls every pane's status updates meanwhile. The user's own "starts with" rules do not see through npx, sudo, .exe paths or bash -c the way the built-ins do. File fencing, secret sealing (DPAPI) and account deletion are solid, with careful rollback and "only delete what Kolux made" checks. Smaller issues: the Codex pill can show another sign-in's figures, account removal can freeze the window and leave the account's sign-in files behind, and on macOS/Linux the pre-trust writes widen ~/.claude.json permissions. Cross-slice notes: links.rs:310 file\_grant persists a fence grant across restarts although the editor button says "for this run", and any window code can grant any local file that way. The two Linux unit-test failures in this slice (codex\_usage, claude\_accounts row989) are Windows-only test assumptions, not product bugs. Most of this slice's tests (protected, secrets, trust, the s9 fuzz suite) never ran on Linux before the container died.

**What is done well:**

- File fence (fence.rs): shares, UNC, \\\\?\ and \\\\.\ device paths and drive-relative or root-relative spellings are refused from the text before any filesystem call; drive roots are never roots; links are resolved before the inside/outside decision; picked-file grants are exact and capped at 100; saves go through temp file and rename, so a dangling link cannot redirect a write.
- Secrets (secrets.rs): DPAPI current-user sealing with CRYPTPROTECT\_UI\_FORBIDDEN; no plain-text fallback on Windows; the window never receives or overwrites secret fields (without\_secrets/keep\_stored\_secrets); clearing a key also removes it from settings.json.bak; API key fields refuse line breaks and huge pastes; the profile folder is restricted to the user (icacls or 0700).
- Accounts: new account folders are claimed with create\_dir so rollback deletes only what Kolux made; removal deletes only &lt;profile&gt;/&lt;accounts&gt;/&lt;id&gt; after safe\_id and parent checks; a failed re-sign-in puts the earlier credentials back byte for byte; links and device codes are scrubbed from error text; the key setup refuses .cmd/.bat/.ps1 launchers rather than going through cmd.exe.
- Protected rules: broad wrapper, encoded-PowerShell, nested and run-together-switch coverage with clear tests; the hook can only ever add an 'ask' and fails open to {} on garbled input; rule switches apply to the very next command; user regex rules use the linear-time regex crate with compile size limits.

## R04-projects-files: Projects, worktrees and file operations

The projects and files area is mostly well built: workspace delete, atomic saves, the path fence, search and clone all show deliberate defensive design. The weak spots are where Windows behaviour or links meet an assumption made on Linux. The worst is that renaming a file in the explorer to another file's name in different letter case silently overwrites that file on Windows and macOS. Next is that a workspace folder renamed by hand is never repaired by the sidebar (contrary to PROJ-068) and is then destroyed at the next launch or by the background tidy. The Explorer's "hide git-ignored files" uses a write-then-read pipe pattern with git that deadlocks on folders of a few thousand entries (reproduced) and can pin the app's async workers; scm\_watch.rs ask\_git has the same pattern (cross-slice). Saving through a symlinked file breaks the link, and the .worktreeinclude copy follows links that its 2 GB budget does not count. Smaller issues: the git search fallback stops at the first non-UTF-8 line; a failed delete has already removed the shared-folder links; an unplugged drive counts as a gone folder; and a failed store read would let the drafts write overwrite every saved draft (rare). Also cross-slice, terminal.rs kill\_under treats two unresolvable paths as the same folder (None == None).

**What is done well:**

- Workspace removal is careful: a stamp of what the dialog showed must still match, Kolux's terminals in the folder are ended and proven gone within 3 s (refused unless forced), locked worktrees are never removed, and the folder goes to a hidden trash in one rename while Git's record is set aside and both are restored if Git still lists it.
- Background trash emptying uses std remove\_dir\_all (which does not follow junctions), a confirmation mark, and a launch sweep that never deletes unconfirmed trash.
- Editor saves are atomic: temp file, flush plus fsync, rename, cleanup of stale copies. A content-hash check refuses to overwrite an agent's newer edit, and saves are serialized.
- The path fence (links.rs) checks both the spelled path and the resolved one, refuses '..' and network shares from the spelling alone, and resolves links for reads, writes and listings.
- Explorer copy, move and create never overwrite (create\_new, existence checks, ' copy N' names), links inside copied folders are skipped, and WSL deletes are flagged as permanent in the confirmation.
- Search runs with a linear-time regex engine, caps on query length and hits, a 15 s timeout that kills the child, cancellation of superseded searches, and '--'/'-e' before user text.
- Clone strips credentials from addresses, puts '--' before the URL, disables prompts, and a cancel ends the whole process tree through a job object.
- Saves of shared lists (projects, groups, statuses, folder ids) start from kept::load, so an unreadable list is an error rather than an empty list saved over the data.
- Repository icons read only plain files inside the repo, never through links. Web icons are fetched in Rust with a public-address-only resolver and size and type caps, and rendered via &lt;img&gt;.

**Not reviewed in this area:** Most #\[cfg(test)\] modules in the slice files (projects.rs 2916-5567 apart from the proj068 test, files.rs 794-1412, and the rest); pr\_checkout.rs and visibility.rs (called from projects.rs but outside the slice); fence.rs beyond check/allow; front-end components for these features beyond the callers listed; No Windows run was possible: the Windows-specific claims (NTFS case-insensitive rename, junction behaviour) rest on documented API behaviour, not on execution.

## R05-git-scm: Git, source control and GitHub

The git and source-control layer is mostly careful. It validates refs, passes paths NUL-separated, parses -z output, never follows links when discarding, uses a confirmed trash for worktree removal, and puts every GitHub call behind one host gate with raw fields and stdin bodies. The most serious problem is in the AI writers: commit message, PR text and auto branch naming run `claude -p` inside the workspace. Claude Code's own docs say print mode skips the folder trust check and still runs the repository's hooks, env block and .mcp.json servers. So a pull request from a fork, opened as a workspace, can run code or redirect the user's Claude credentials once they ask for an AI commit message. Several reliability problems follow: the watcher starts one git per changed file under heavy folders inside a submodule (git refuses those paths and the failure is never cached); writers that take the prompt as an argument cannot start when installed as a Windows .cmd launcher; and the fetch before a workspace create or PR open has no time limit, no prompt guard and no cancel while it holds the project's create lock. Smaller issues: a linked worktree's ignore cache ignores edits to the shared exclude file, a raw NUL byte hides half of scm.rs from grep and ripgrep, All Changes re-reads untracked files without a size cap, printed PR links overwrite hand links, and git inherits GIT\_DIR from whoever launched the app. Cross-slice notes: SAFE-023's pre-trust of new worktrees (trust.rs) gives interactive agents the same repository-settings exposure and should be weighed with the writer fix. The Abort merge/rebase button calls scm\_abort with no confirmation, which can throw away conflict resolutions. On Unix, procs::kill\_tree's group kill does nothing for git's timeout path because git is not a process-group leader; I did not tie this to the container crash.

**What is done well:**

- Argument hygiene is consistently good. Refs are checked by Git::ref\_ok and `--end-of-options` before they reach git. Stage, unstage and discard pass paths NUL-separated on stdin with --literal-pathspecs. Status, diff and ls-files are parsed in -z form, including renames, so spaces, quotes and non-ASCII names come through intact.
- Discard is careful: paths must be plain relative components, links are removed as links and never followed, the untracked section goes through `git clean`, and the front-end dialog spells out what is lost.
- Worktree removal goes through a hidden trash with undo. Git's record is only set aside until removal is confirmed, the launch sweep deletes only confirmed trash, the main checkout is refused, and kept branches are deleted later only by compare-and-delete (update-ref -d with the old commit).
- Short git reads get a per-worktree concurrency limit with foreground priority, plus a 90 s limit that kills the whole process tree.
- The gh runner has prompts off, a 30 s limit, a kill-on-close job on Windows, and drains its pipes on separate threads.
- GitHub access goes through one host gate (host\_allowed). Values are sent as raw -f fields and request bodies as JSON on stdin. Merges are pinned to the shown head sha, need an explicit confirmation, and must target a registered project's remote.
- The PR-from-fork checkout never reuses a stale local branch and keeps refspecs and remote names safe. The .worktreeinclude / kolux.yaml lists are read from the main checkout, not from the PR's files.
- The Windows folder watcher handles overlapped I/O correctly (cancel and wait before the buffer is freed), handles buffer overflow, falls back to polling for network or junction paths, and has a wake event so removal can join the reader threads.

**Not reviewed in this area:** Most #\[cfg(test)\] modules: git.rs 1115-1684 beyond the tests named above, scm.rs 2778-5187 beyond git017\_d/git026, scm\_watch.rs 918-1756 beyond t033f, github.rs 775-1356, pull\_requests.rs 799-1327, pr\_review.rs 753-1170, pr\_checkout.rs 297-537, scm\_writers.rs 575-772, scm\_recipe/stack/repo\_id/open/star tests; Front-end Source Control components beyond the discard, oneClick, autoBranch and All Changes pieces (other slice); No build or test runs and no live git network runs (by rule).

## R06-terminal-process: Terminals, PTYs and processes

The terminal and process layer is carefully built for Windows: per-pane job objects, bounded buffers, flow control and disciplined lock ordering in the window, many already tested. The container-wide crash during the Linux unit tests came from procs.rs's Unix tree kill: it runs `kill -9 -<pid>` without `--`, and the Debian/Ubuntu kill reads only the first digit, so once the git test pids passed 10000, a timed-out git test sent kill -9 to every process. Windows, the shipping platform, uses taskkill and is unaffected; anyone running the tests or a Linux build on Debian or Ubuntu is exposed, and on macOS the group kill silently misses the children of git and setup scripts. The most serious Windows risk is that the background terminal service closes a pane's console while holding the lock every pane's output needs, which can freeze all terminals on Windows 10 and pre-24H2 Windows 11 when the closing pane is busy printing. Smaller issues: the zsh integration leaves ZDOTDIR on Kolux's folder (Mac history and installer edits go astray), the bash hook replaces users' DEBUG traps (Git Bash too), and the service's pre-token reads and Linux token-file mode are looser than its header promises. Cross-slice: newproject.rs and agent\_install.rs keep their own kill\_tree copies (bare-pid kill on Unix; taskkill even on macOS and Linux, where it does nothing), newproject keeps a reaped clone pid for up to 2 s, launch\_detached does not detach on Unix, and lifecycle::claim\_named is a no-op on Unix.

**What is done well:**

- Windows Job Objects are handled carefully: a kill-on-close job per pane, assigned by process handle so a reused pid can never be pulled in, and an app-wide job that allows breakaway only for the terminal service. Every unsafe block carries an accurate SAFETY note and handles are closed once.
- The window registry follows a strict rule ('Row 784'): PTY teardown runs only after the registry lock is released, and tests simulate a stalled ClosePseudoConsole to prove it.
- Buffers are bounded throughout: a 4-deep reader queue (pty\_pump.rs), the OutputLog line and pending caps, the history file cap with temp-file compaction, EARLY\_CAP for early events, and flow control that pauses a flooding reader but never holds it for good.
- pty\_service::stop never kills a pid it has not proven through the token handshake, and runs every probe and wait against one deadline.
- Pane environments are cleaned of Tauri, WebView2, cargo, npm and conda variables and of another copy's data-folder override. The PowerShell hook travels as -EncodedCommand. Session ids read from untrusted pane output are validated by safe\_session before they can reach a cmd /c shim.
- Riskier helpers are written defensively: update\_guard passes the file path to System32 PowerShell through an environment variable with a bounded wait; term\_import fails closed with real-path containment and size caps; the crash-dump parser is fully bounds-checked.
- scm.rs already knows the correct `kill -9 -- -pid` form and documents why; the fix for F1 exists in the codebase.

**Not reviewed in this area:** #\[cfg(test)\] modules of the slice files, except the coverage checks named above; src-tauri/src/pty\_resize\_tests.rs and src-tauri/src/terminal/flood.rs (test-only); src-tauri/src/resources/recovery.rs 660-1471 (crash records, safe-graphics flags, memory samples); src-tauri/src/resources/update\_care.rs and provider\_usage.rs bodies; front-end terminal TypeScript (outside this slice).

### R06-terminal-process.5 The terminal service reads a connection's first line before checking the token, with no time limit or size cap, one thread per connection

- **Severity after checks:** low · **Check:** not double-checked (the auditor rated it low) · **Kind:** security
- **Where:** `src-tauri/src/pty_service.rs:401`
- **What you would notice:** Another user signed into the same Windows computer could crash Kolux's background terminal process, which ends all your running agents.
- **How it happens:** Any local process can connect to the service's 127.0.0.1 port; on Windows, loopback is shared with other signed-in users. run() spawns a thread per connection (450), and serve() also calls next\_conn(), which takes the lock, then reads the hello with BufReader::lines(): no read timeout and no length cap. A peer that streams bytes without a newline grows the service's memory until it fails; a peer that opens thousands of silent connections pins thousands of threads. - **Code:** `let mut lines = BufReader::new(stream).lines(); let hello: Value = lines.next().and_then(Result::ok)...`
- **Suggested fix:** Set a short read timeout and a byte cap (for example 4 KB) on the hello line, keep the cap on later lines, and limit concurrent unauthenticated connections.

## R07-browser: The built-in browser

The built-in browser is carefully built for the obvious attacks. Address-bar and redirect isolation, icon fetching, certificate trust, permission prompts and download naming each have explicit rules and unit tests, and the production code has no panics. The biggest open risk is iframes. Tabs block Kolux's own app address (http://tauri.localhost) only for whole-page navigation, never inside a frame. On Windows the Tauri command bridge is injected into every frame, so a website can probably embed a live copy of Kolux with full command access. That needs a quick live check and a one-line frame rule. Several smaller gaps let pages act without the user. Popups and system-browser windows open without a click (WebView2 turns off Edge's popup blocker), page-made menu picks and shortcut messages are trusted too easily, credentials an agent sets leak to later sites, SmartScreen is off, and an allowed preview folder can be uploaded by its page. Functional bugs: the Ports panel and Preview button fail on non-English Windows, history titles are shifted by one page, and history and tab-trail saves can corrupt each other. Lower-confidence notes left out of the findings: the preview server's token is a predictable hash of the folder path and it ignores the Host header (a DNS-rebinding risk from browsers without private-network protection); by default every workspace shares one cookie jar, which is also the Kolux window's own; process-to-workspace matching in ports.rs trusts parent PIDs, which Windows reuses.

**What is done well:**

- Main-frame isolation is consistent: the address bar, redirects, links, window.open, popups and `kolux goto` all go through allowed(), which keeps tabs off \*.localhost and the dev origin, and unit tests cover the spellings (trailing dot, case, ports).
- The favicon fetcher is a careful SSRF design: a public-only DNS resolver for other hosts, redirect rules applied on every hop, local fetches only for local pages on the same host and port, size and time caps, and no fetch that goes around a configured proxy.
- Certificate trust is narrow: https on this computer only, per host, port and fingerprint, only after a real engine challenge, revocable. Every other bad certificate in a tab is cancelled.
- Every permission request (camera, microphone, location, clipboard read, notifications and the rest) is denied, with a plain-words notice in the pane; previews deny everything.
- Downloads get safe, non-overwriting names with a bounded clash loop, and are never opened by Kolux.
- Destructive file and process actions are well guarded: profile folders are removed only after canonicalisation inside the profiles folder, and leftover helper processes are killed by pid plus start time plus program name, never by name alone.
- Data the app hands into page scripts is always JSON-encoded, so no code injection. There is no unwrap, expect or panic in production paths, and the 280 browser unit tests pass on Linux.

**Not reviewed in this area:** #\[cfg(test)\] modules beyond spot checks for coverage; src-tauri/src/browser\_cli.rs (not in this slice; only its emulation state was read); resources/recovery.rs beyond the browser-argument builder; Nothing was run live: every engine behaviour above comes from reading code, library sources and Microsoft docs.

## R08-orch-auto-chat: Orchestration, automations, chat and session resume

This area is carefully written and mostly defensive: corrupt store values are kept aside instead of overwritten, the automation clock handles daylight-saving changes and missed runs without replaying a backlog, transcript readers cap what they read and skip bad lines, and session ids are validated before any resume. The serious problems come from changes elsewhere that this area did not follow. Terminals now keep running after Kolux quits, but orchestration still ties each helper agent to the app's process id: after a reopen every running helper is declared cut short and its reports are ignored. Automations' reconnect also races the terminal service hand-back. On Windows, agents installed through npm (including Gemini as Kolux installs it) get their opening prompt through cmd.exe, which keeps only the first line, so helper briefs, automation event lines and carried conversations arrive incomplete. The mail pointer can spin a CPU core when an idle agent's screen contains a permission-like phrase, and the usage-limit auto-continue types its message without the pause before Enter that the rest of the code relies on. Cross-slice notes: pty.rs's cmd-shim comment understates the quoting problem (any argument with a space plus a profile folder with a space stops the agent from starting); scm\_recipe.rs says no shell is involved although .cmd agents go through cmd.exe; agents::tests::each\_parent\_folder\_is\_asked\_for\_a\_marker\_at\_most\_once\_per\_pass fails on Linux only because it uses Windows backslash paths. Another auditor (P2) found the same .cmd truncation from the multi-seat launch side.

**What is done well:**

- Store blobs that no longer parse are copied aside byte for byte before a fresh value is written (orchestration/kept.rs), saves refuse while the mail could not be read, and the orchestration store upgrade is one transaction with per-layout backups.
- The automations clock avoids catch-up storms: after sleep or downtime each automation either runs once inside its grace window or logs one 'missed' entry and moves on; DST gaps and overlaps go through jiff's compatible disambiguation; timetables have length, horizon and period caps with plain-language errors.
- Transcript readers are defensive: bad JSON lines are skipped, a half-written last line is held back, rotation and truncation are detected, and first reads, pages, tool output (20k), diff work (250k cells) and images (4 MB, data:image/ only) are capped.
- Session ids are checked by safe\_session before any resume, lookup or carry, and no transcript path is sent to the window; session\_rows never probes network paths.
- The runtime file commands confine paths to the worktree both as written and after following links, and refuse drive-relative and root-relative paths.
- The send-once state machine has bounded waits, never presses Enter twice, and refuses to paste over a visible permission prompt; the automation precheck runs without a console window and is killed as a whole tree at its limit.

**Not reviewed in this area:** Most #\[cfg(test)\] module bodies in these files; orchestration/teams.rs body; Front-end chat, automations and sessions views (src/chat, src/automations) that consume these commands; Live behaviour on Windows (no build or run was possible here); the Claude Code paste/Enter behaviour behind the resume.rs finding is inferred from the code base's own ORCH-055 rules, not observed.

## R09-app-core-install: App core, state, updates and installers

The start-up, settings and quit paths in this slice are careful: damaged settings or state files are set aside instead of overwritten, the final save is bounded, and repository scripts and agent installs are gated by trust and by a reviewed allow-list. The serious problem is a bad interaction. Since T-184 the whole app runs inside a Windows job that kills every member when Kolux exits, and both the update installer (started by the updater plugin just before it exits) and the restarted copy (app.restart) stay in that job, so updates and the safe-graphics restart cannot work on Windows. The only live update proof predates the job and used a stub installer. The same root cause, in another slice, means editors, browsers or files that Kolux opens fresh (links.rs spawn\_editor, open\_path, artifacts::system\_open) are also killed when Kolux quits; that slice's owner should check it. The other issues are medium or low: a global store lock held across per-project git runs (UI freezes, hook answers that time out), artifact pages that can open browser tabs without a click, untested parallel vendor installers, a log-rotation naming flaw that explains the app041 test failing on Linux, and a loose CDN prefix check. IPC exposure of app commands to browser-tab subframes is already covered by the R07 and L1 auditors and is not repeated here.

**What is done well:**

- Settings are saved all-or-nothing (temp file, fsync, rename) with a last-good .bak; a failed read blocks every later save, so defaults never overwrite a real file; a damaged state.db is checked with quick\_check, set aside and restored before the store opens.
- The final save at quit runs each step on its own thread under one shared deadline with panics caught, and a quit watchdog guarantees the process ends.
- Updater: minisign key built in (empty key = no updates), requireSignedVersion honoured by the plugin, HTTPS feed, test feed only in debug builds, plus an Authenticode publisher pin on the downloaded installer.
- Repository scripts (kolux.yaml setup, issue command, default tab commands) need the user's trust, remembered by SHA-256 of the shared text alone; tab commands are stripped until trusted; a local override must be untracked and not a link.
- Agent installs come from a fixed table held by a separate reviewed allow-list test (exactly one https URL per script, exact npm/winget/uv ids), with deadlines, tree kill, and no admin prompt in silent mode.
- The importer from the former product reads one settings file through an allow-list with shape checks and secret-name/value refusals, follows no links and caps sizes.
- Main-window navigation allows only the exact app origin (no userinfo or port); web and mail go to the system browser and everything else is blocked; capabilities are minimal and the updater/notification JS APIs are not granted.

**Not reviewed in this area:** Test modules in the slice files, except to check coverage of suspected bugs (lifecycle.rs 717-950, agent\_install.rs 886-1509, onboarding.rs 570-966, setup.rs 1478-2586, import.rs 550-983, tray.rs/menu.rs tests); Vendor install scripts themselves (not opened, clean-room rule), so the Path-editing behaviour in finding 4 rests on the code's own comments; No live Windows run: findings 1 and 2 are code- and documentation-verified, not observed.

## R10-skills: Skills and kits

The delete engine (skill\_delete.rs) is the strongest part of this area: journaled, crash-safe, careful with links, junctions and network shares, heavily tested. I found no way for it to remove anything except the skill the user picked; its only gaps are a rare failure path that hides a skill while reporting no change, and a slow walk through crafted link mazes. The weak part is everything that talks to the third-party community skills installer, which was built against a stand-in and never checked against the real tool. Install commands, including onboarding's, point at a GitHub repository the project's own records say does not exist yet. The update check compares the installer's recorded hash with a different hash Kolux computes, so updates can never be offered. The CLI's `--local` and Kimi flags mean something else to the installer. On Windows the installer is started as a bare `npx.cmd` through cmd.exe, so a planted npx.cmd in the current project folder would run instead. Separately, the WSL skill scan runs commands inside WSL distributions against your confirmed decision OD-12, and has never run on a real distribution. Cross-slice: no code renders skill or kit Markdown to HTML any more (the kits code is gone, and the front end shows skill text through React without innerHTML), but pulldown-cmark is still a dependency in src-tauri/Cargo.toml:59 with no user; none of the 115 skill Rust tests ran on Linux because the container restarted.

**What is done well:**

- skill\_delete.rs is a careful all-or-nothing engine: each item is renamed aside next to where it sits, a journal records every move, a failed rename puts back what already moved, and startup finishes or undoes an interrupted delete under the shared lock. I found no path that removes anything except the chosen skill's folder, links and receipt.
- Removing a link never touches its target: symlink\_metadata decides, and junctions count as links. Before every rename attempt the folder an item sits in is checked again against the scanned roots. Journal entries are trusted only if they carry the exact set-aside name next to their original and sit under a vouched-for skills folder.
- Network shares are never touched: a path's text is judged before any disk call, and each link hop is resolved and judged. The rule is applied the same way in scan, reveal, plan and the update check.
- The scan gives every root its own thread with an 8 s limit and a cancel flag. The WSL answer parser is strict: a cut-off or garbled answer becomes an error, never an empty list. Distribution names are validated and wsl.exe gets its arguments as argv; no shell string is built.
- Installer argument hygiene: skill and agent names are limited to \[A-Za-z0-9.\_-\], cmd.exe metacharacters are refused before a command line is built, Stop kills the whole process tree, and captured output is capped at 1 MB.
- One OS-level file lock (try\_lock) is shared by delete, install and update across the app and the CLI. The OS releases it if the holder crashes, so skill operations cannot stay stuck.
- No unwrap, expect or panic on production paths. Poisoned mutexes are recovered, and corrupt dismiss lists are moved aside rather than overwritten.
- About 60 delete tests cover crash-mid-delete in a child process, link swaps between renames, stale and refused journal entries, and lock contention.

**Not reviewed in this area:** skills.rs tests from about line 940 to 1321, and the full bodies of the installer.rs/update.rs/cli\_install.rs tests; Windows runtime behaviour (nothing could be run here), including how wsl.exe parses the quoted script argument; crate::procs::kill\_tree, crate::grok::home, crate::diag, and the front-end SkillUpdate/SkillInstall/notice components beyond their command calls; Tauri capability scoping of these commands (cross-slice, L1/R09).

- **What you would notice:** A downloaded project with a crafted maze of folder links can make the Skills page's Delete button spin forever and use a lot of CPU while that project is open.
- **How it happens:** occurrences() (skills.rs:747-781) only skips a link that points back at one of its own ancestors. It keeps no global visited set and, unlike the list scan, has no time limit or cancel flag. plan() calls it for every deletable root, including the open project's .claude/.an audit test file skills folders (skill\_delete.rs:951-953), and run() does so while holding the shared skill lock. Take a project folder holding N subfolders, each with N links to its siblings: the walk revisits the same real folders through every path to depth 4, roughly N^5 entries, each costing several file-system calls. With N=30 that is tens of millions of entries, so the Delete confirmation never appears and a CPU core stays busy until the walk finishes. The list scan (walk(), with a global `seen` set and the 8 s limit) shows the same folder fine. Reaching this needs a repository checked out with symlinks: the default on macOS and Linux, opt-in on Windows.
- **Code:** `let Some(c) = canon(&p) else { continue }; if chain.contains(&c) { continue; } ... } else if depth > 0 { chain.push(c); every(&p, depth - 1, chain, out)?; chain.pop();`
- **Suggested fix:** Recurse into each real folder once (global set of canonical folders) while still recording every link path that reaches a skill folder. Also give occurrences() the same time limit or entry budget as the list scan, and report a clear error when it is hit.
